# EMQX 拆分部署的可选宿主机网络对照

日期：2026-11-02。状态：各三轮6000台对照已完成，bridge三轮通过、host仅一轮通过，未取得稳定收益，已恢复bridge。
另完成bridge的6500台首轮通过；未重复、不称最大容量。最终证据见 `docs/test-reports/2026-11-02-emqx-network-ab-results.md`。

## 目标与依据

前序报告 `2026-11-01-ladder-1s-higher.md` 中，6000 台每秒一条时 EMQX VM
软中断占比高、接收环缺缓冲丢包，而应用 VM 有余量。新增可回退的 Linux host 网络选项，
用于检验去掉 Docker bridge/DNAT 是否改善当前环境的收包开销。不能预先保证提升，
也不能由虚拟化环境结果外推生产容量。

## 实施范围

- 仅增加 `deploy/split/emqx/docker-compose.host.yml`；默认桥接不变。
- 使用 `!reset` 清除继承的 `ports`、`networks`、网络 `sysctls`。
- MQTT/Dashboard 显式绑定现有地址与端口变量；关闭此前未发布的 SSL/WS/WSS 默认监听器。
- 节点名、数据卷、ACL、HTTP 鉴权、共享订阅及应用代码保持原样。
- 不自动修改 RPS/RFS、网卡环大小、宿主机 sysctl，不升级镜像，不推送代码。
- host 模式还需检查集群/RPC 和自定义监听器的暴露与端口冲突，不能等同于原 bridge 的端口发布边界。

## 运行验收与性能对照

1. 核实实时部署目录和部署版本，记录容器与镜像身份。交接中的旧路径不可直接照抄。
2. 记录宿主机 CPU、每核 softirq、接收环、队列分布、缺缓冲丢包和 TCP 重传的基线。
   用差值而不是中断累计值判断当前负载分布。
3. 先做独立临时容器的启动/监听器检查，再在实验室环境停发压、排空后切换。
   内存会话不能跨 EMQX 重建保留，所有测量窗口必须在设备与共享订阅恢复后重新开始。
4. 保持设备集、消息负载、镜像、资源、发压机和其他服务状态相同；A=bridge，B=host。
   先 5000 台 × 每秒一条做基准，再 6000 台 × 每秒一条验证原失败档。
   每轮保持 300 秒，交替 A/B 至少各 3 次；每档后排空并核对结果。
5. 同时比较设备实际发送/确认、掉线、确认 p99、实际 InfluxDB 数据、积压、死信、
   丢弃、主机 CPU/softirq 与缺缓冲丢包。用唯一设备/时间窗（最好带序列）核对消息；
   单纯行数大于确认数不能证明每一条已确认消息都存在。
6. p99 明确为 PUBACK 延迟；另记录已有入库延迟，二者不可混称端到端查询延迟。
   对照未通过或收益无重复性时恢复 bridge，不据单次峰值修改容量结论。
7. 临时停用的其他容器必须恢复，最终网络模式、服务状态与未验收项写入报告和同一交接。

## 可复现演示

复用 `docs/script/loadtest/ladder.py` 与已有压测专用产品/设备；设备和凭据从本地忽略文件读取。
不新增业务种子，不覆盖设备密钥。演示操作为切换两个 Compose 文件组合、回读网络模式，
再用相同阶梯命令对照 `summary.md` 和监控指标。首次配置解析验证不创建业务数据或 agent。

## 当前证据

`verify_host_network.py` 在真实 Docker Compose 上验证四种组合，确认 bridge 保留映射和 sysctl，
host 清空冲突配置并遵循自定义端口；报告见 `docs/test-reports/2026-11-02-emqx-host-network.md`。
尚无容器启动、鉴权回调、监控或吞吐收益的验证结果。
