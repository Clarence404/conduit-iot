# V0.4-A1 单设备指令 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 运维人员在设备详情页对一台在线设备调用物模型「服务」，几秒内看到设备的执行结果，并留下指令记录。

**Architecture:** server 校验并落库 `device_command`（PENDING），事务提交后写下行流 `conduit:stream:down`；transport 消费下行流、用持有的 MQTT 连接以 QoS 1 发到 `conduit/{pk}/{dk}/down/service`（带 MQTT 5 消息过期间隔），并把发送结果作为 `COMMAND_DISPATCH` 写回上行流；设备回执 `up/reply` 作为 `COMMAND_REPLY` 走上行链路；server 流水线按状态改写规则更新记录，守护线程做超时清扫。

**Tech Stack:** Java 21、Spring Boot 3.5、MyBatis-Plus、Flyway、Redis Streams（Lettuce / `StringRedisTemplate`）、HiveMQ MQTT 5 client 1.3.7、Vue 3 + TS + Element Plus、Vitest、Testcontainers。

**Spec:** `docs/superpowers/specs/2026-11-25-conduit-v0.4a1-device-commands-design.md`

## Global Constraints

- 下发 topic `conduit/{productKey}/{deviceKey}/down/service`，QoS 1；回执 topic `conduit/{productKey}/{deviceKey}/up/reply`，QoS 1。
- 下发 payload：`{"id","service","params","ts","expiresAt"}`；回执 payload：`{"id","code","message","data"}`，`code` 整数，0 成功、非 0 失败、`-1` 为设备判定过期未执行；`message` ≤ 256 字符；`data` 为 JSON 对象，序列化后 ≤ 4 KiB。
- 指令 id：`c-` + ULID（26 字符），即协议中的 `id`。
- 状态：`PENDING`、`SENT`、`SUCCEEDED`、`FAILED`、`TIMED_OUT`、`NOT_SENT`；`failure_reason`：`NO_SUBSCRIBER`、`EXPIRED_BEFORE_SEND`（NOT_SENT），`NO_DISPATCH_REPORT`、`TAKEOVER_UNKNOWN`（TIMED_OUT）。
- **只有确定证据才判 NOT_SENT；其余不确定一律 TIMED_OUT（结果未知）；之后更确定的证据可以改写**（spec 5.3 的改写规则逐条实现）。
- 服务：标识 `^[A-Za-z][A-Za-z0-9_]{0,63}$`，产品内唯一；名称 ≤ 64、描述 ≤ 256；输入参数最多 16 个，类型 DOUBLE / INT / BOOL / TEXT / ENUM，约束规则与属性相同；`timeout_seconds` 5～60，默认 10。
- 同一设备未结束（PENDING / SENT）的指令最多 5 条；记录保留 90 天；清扫每 2 秒，PENDING 宽限期默认 30 秒（`conduit.command.dispatch-grace`）。
- 下行流 `conduit:stream:down`，`MAXLEN ~ 100000`，消费组 `conduit-transport-down`，消费者名为 transport 的 instanceId；认领空闲 ≥ 10 秒的条目。
- 权限：下发 `device.command`；查询 `device.read`；服务定义读 `product.read`、写 `product.manage`。授权模式与其他写操作一致（`shadow` 下按旧路径矩阵：租户管理员可下发、只读不可）。
- 新增死信原因：`INVALID_REPLY`、`UNKNOWN_COMMAND`。
- 每个类写中文 Javadoc，重点方法写注释（CLAUDE.md 2.1）；日志遵守 CLAUDE.md 2.2：每条下发记一行 INFO（指令 id、设备、服务、操作人），不记参数值与回执 `data`。
- 先写失败测试（TDD）。提交遵循 Conventional Commits，不加任何 AI 署名行。仓库公开：不提交 IP、本机路径、口令。
- 本机 shell 默认 JDK 不是 21：`export JAVA_HOME=/c/Users/ChenHan/.jdks/ms-21.0.8`；Maven 一律 `-o`。
- 本机没有 Docker：实现者只跑单元测试并保证集成测试能编译；集成测试与 e2e 由 controller 在 129 的 `maven:3.9.9-eclipse-temurin-21` 容器里跑（做法同 `docs/test-reports/2026-11-16-transport-internal-listener.md` 第 2 节）。

## Review Focus

1. 参数里传入嵌套对象、数组、超长 TEXT、未定义的多余参数或 INT 字段传小数：一律 400 并指出参数名，不落库（Task 3 测试）。
2. 设备回执别的设备的指令 id、或回执已删除设备的指令：进死信 `UNKNOWN_COMMAND`，不改任何记录（Task 5 测试）。
3. 服务定义在指令下发后被改名或删除：已有记录保留快照，回执照常更新状态（Task 5 测试）。
4. transport 本实例没有已连接身份时，下行条目留在流里由其他实例处理，不被读走后发不出去（Task 6 测试）。
5. 用户离开控制标签或切换设备时，状态轮询立即停止，不留后台计时器（Task 8 测试）。

**Files:**

**Interfaces:**
- Consumes: Task 1 `CommandDispatch.parse`、`MessageType.COMMAND_*`；Task 4 实体与 mapper；`PipelineProcessor` 的 `dead(...)`、`backoff.run`、身份预取（`DeviceIdentity.tenantId()`）。
- Produces:
  - `CommandTransitions`（纯函数）：`static Optional<Change> onDispatch(Status current, Outcome outcome, String reason, long at, long expiresAt)`、`static Optional<Change> onReply(Status current, int code)`、`static Set<Status> sweepableSent()` 等；`record Change(Status to, String failureReason, boolean late, boolean overturnedNotSent)`。规则严格按 spec 5.3：
    - 回执：PENDING / SENT / TIMED_OUT / NOT_SENT → SUCCEEDED（code=0）或 FAILED；源为 TIMED_OUT 或 NOT_SENT 时 `late=true`；源为 NOT_SENT 时 `overturnedNotSent=true`（记 WARN）；SUCCEEDED / FAILED 时不变。
    - SENT 报告：PENDING / TIMED_OUT → SENT，若 `at > expiresAt` 则 → TIMED_OUT 并记 `sent_at`；其他状态不变。
    - NOT_SENT 报告：PENDING / TIMED_OUT → NOT_SENT（带原因）；其他不变。
    - UNKNOWN 报告：PENDING → TIMED_OUT（带原因）；其他不变。
  - `CommandStatusUpdater.applyDispatch(long tenantId, String deviceKey, CommandDispatch.Parsed d) → boolean`、`applyReply(long tenantId, String deviceKey, Reply r) → boolean`：读当前状态 → `CommandTransitions` → 带源状态条件的 `UPDATE ... WHERE id=? AND tenant_id=? AND device_key=? AND status=?`（乐观并发，竞争失败重读一次）；找不到记录返回 false。
  - `CommandReplyParser.parse(byte[] payload) → Reply`：`record Reply(String id, int code, String message, JsonNode data)`；不合法抛 `DecodeException(DeadReason.INVALID_REPLY, ...)`。
  - `PipelineProcessor`：`COMMAND_REPLY` → 解析 → 身份 → `applyReply`，false 时 `dead(UNKNOWN_COMMAND)`；`COMMAND_DISPATCH` → `CommandDispatch.parse` → 身份 → `applyDispatch`，false 时 `dead(UNKNOWN_COMMAND)`；两者成功后与 presence 一样批末统一 ack，数据库异常走 `backoff.run` 原地重试。
  - `CommandSweeper`（`ThroughputSampler` 同款守护线程）：每 `sweepInterval` 执行 `SENT ∧ expires_at < now → TIMED_OUT`、`PENDING ∧ expires_at + dispatchGrace < now → TIMED_OUT(NO_DISPATCH_REPORT)`；每天一次删除 `created_at < now - retention`。经 `TenantContext.callAsSystem("command-sweep", …)` 执行。
