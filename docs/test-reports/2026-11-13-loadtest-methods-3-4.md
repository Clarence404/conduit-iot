# 测法三（连接形态对照）与测法四（真实设备画像）压测报告

- 日期：2026-11-13
- 计划：[`2026-11-12-loadtest-methods-plan.md`](../superpowers/plans/2026-11-12-loadtest-methods-plan.md)
- 测试类型：测法三为**回归对比**（同一总速率、不同连接形态）；测法四为**容量测试**（按设备画像长时间运行，含 2 小时浸泡）
- 判据：`docs/script/loadtest/README.md` 的 7 条（计数守恒、无掉线、p99 ≤ 1 秒、积压 ≤ 5 秒流量、EMQX 无失效日志与过载告警、结果可信）

## 1. 结论

**测法四（对外容量口径）**：拆分部署在本地两台 8 vCPU VM 上，以下三档全部通过，计数守恒，零掉线，零丢弃。

| 档位 | 设备数 | 时长 | 消息/秒 | PUBACK = InfluxDB 行 | 入库 TPS | p50 / p95 / p99 ms | 应用主机 / EMQX 主机 CPU | 可靠上报回执 |
|---|---|---|---|---|---|---|---|---|
| 1 | 10,000 | 30 分钟 | 783 | 1,386,235 = 1,386,235 | 788 | 4.4 / 22.5 / 30.8 | 12% / 12% | 663,477 / 663,477 |
| 2 | 25,000 | 30 分钟 | 1,958 | 3,420,369 = 3,420,369 | 1,918 | 6.2 / 28.0 / 37.5 | 27% / 28% | 1,691,691 / 1,691,691 |
| 3 | 10,000 | 2 小时浸泡 | 783 | 5,544,951 = 5,544,951 | 788 | 4.6 / 24.6 / 31.1 | 14% / 13% | 2,653,916 / 2,653,916 |

画像：每条 30 个测点；上报间隔 70% 每 60 秒、25% 每 15 秒、5% 每秒（每台平均每秒 0.07833 条）；一半设备带 `id` 走可靠上报并订阅回执。

对外表述：**2.5 万台、按上述混合间隔、每条 30 个测点，30 分钟无损；1 万台同画像 2 小时无损，内存与积压不随时间增长。**
两档都远未到瓶颈（两台 VM 的 CPU 不到 30%），上限没有测到；本机发压端的限制见第 4 节。数字只代表本地虚拟化环境，不外推到物理机或云主机。

**测法三（连接开销）**：总速率同为 5,000 条/秒，连接数从 1,000 增到 5 万，EMQX 主机 CPU 从约 30% 涨到约 52%，EMQX 内存从 0.57 GB 涨到约 3.6 GB（每条连接约 70 KB）。
5 万连接那组出现总线积压，但当时宿主机已打满，结果不可信，只能作为线索。

## 2. 环境与版本

- 部署：`deploy/split`。EMQX 主机 VM（8 vCPU）只跑 `conduit-emqx`；应用主机 VM（8 vCPU）跑 server、两个 transport、PostgreSQL、Redis、InfluxDB、Prometheus 等。发压机为同一台物理机（Windows）。
- 代码：`main` 的 `5188a08`；transport 为含积压与节点内存告警的版本（`2e6b882` 起）。发压工具为本次提交的 `loadgen.py` / `ladder.py`。
- EMQX 会话参数取自 `deploy/split/emqx/.env.example`（`2e6b882` 起）：`max_inflight` 1024、`max_mqueue_len` 50000、`max_mailbox_size` 10000、开启 `force_shutdown`；transport `batch-size` 512、4 条连接。
- 与测试无关的容器（两台 VM 上的其他业务）在测试期间保持停止，按所有者要求暂不恢复。

## 3. 测法三：同一总速率、不同连接形态

命令（`docs/script/loadtest` 目录，各稳态 300 秒）：

```bash
python ladder.py run --devices 1000 --rate-plan 5 --hold 300 --out results-shape-A
python ladder.py run --plan 5000 --rate 1 --hold 300 --per-process 500 --out results-shape-B
python ladder.py run --plan 50000 --rate 0.1 --hold 300 --per-process 2500 --out results-shape-C
```

运行期间另以 `/proc/stat` 与 `top` 每分钟采样 EMQX 主机。

| 组 | 形态 | 结论 | PUBACK = 行数 | 入库 TPS | p99 ms | 积压峰值 | 应用主机 / EMQX 主机 CPU | EMQX 主机 softirq | EMQX 内存（RSS） | 发压进程 最忙单核 / 合计 | 宿主机 CPU 平均 / 峰值 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| A | 1,000 × 每秒 5 条 | ✅ | 1,499,992 = 1,499,992 | 5,021 | 9 | 6,528 | 25% / 31% | 约 12% | 0.57 GB | 26% / 1.3 核 | 46% / 92% |
| B | 5,000 × 每秒 1 条 | ✅ | 1,499,988 = 1,499,988 | 5,019 | 52 | 8,921 | 41% / 43% | 14～21% | 1.2 GB | 42% / 4.2 核 | 75% / 99% |
| C | 50,000 × 每 10 秒 1 条 | ❌ 不可信 | 1,499,953 = 1,499,953 | 4,490 | 43 | 155,220 | 43% / 53% | 约 17.5% | 3.5～3.6 GB | 69% / 13.4 核 | **89%** / 99% |

解读：

- 三组计数全部守恒，均无掉线、无丢弃。
- 连接越多，EMQX 越吃 CPU 与内存：同样每秒 5,000 条，5 万连接时 EMQX 主机 CPU 是 1,000 连接时的约 1.7 倍，内存约 6 倍。这部分开销与消息量无关，是按连接数计的。
- C 组积压 15.5 万条、入库 TPS 4,490，低于发出速率。可能原因是 5 万台不同设备使同批内最新值合并的效果下降、流水线每批工作量变大；但宿主机 CPU 平均 89% 超过 85% 的可信线，被测 VM 抢不到 CPU，**不能据此判定后端在 5 万连接下跟不上**。
- 计划中引用的早先观察「1,000 × 5 的 p99 为 559 毫秒，高于 5,000 × 1 的 15 毫秒」与本次同时段对照相反（A 9 毫秒、B 52 毫秒）。本次三组在同一配置、同一时段连续运行，以本次为准。

无效的第一次运行（如实记录）：13:18 起的第一轮中，B、C 两组的发压进程数不足。

- B 组：每进程默认 1,000 台，p99 4,583 毫秒，判为不合格，发压进程合计 3.5 核、宿主机 80%。
- C 组：最忙发压进程单核 92%，34,761 台掉线，判为结果不可信。

A 组在第一轮有效，沿用其数据。B、C 改为 `--per-process 500` 与 `2500` 后于 13:45 重跑，即上表数据。

另：EMQX 主机网卡 `pkts rx OOB` 的采样器读出的增量为负值，采样方式不可靠，本次不使用这一列。

## 4. 测法四：真实设备画像

### 4.1 工具改动（本次提交）

- `loadgen.py`：压测产品物模型扩为 30 个三相电表测点（前 3 个与原来相同，`provision` 补建缺少的属性）；新增 `--points`、`--mix`、`--id-ratio`。设备间隔按序号确定性分配。带 `id` 的设备在连接后订阅 `conduit/{productKey}/{deviceKey}/down/ack` 并统计回执。
- `ladder.py`：透传三个参数；`--mix` 时档位速率按画像平均速率计算；输出增加「可靠上报回执 / 带 id 发出」。
- 冒烟（1,000 台，2 分钟）：8,656 = 8,656 行，抽查每行 30 个测点齐全，回执 4,162 / 4,162。首次冒烟时带 `id` 的设备没有订阅回执，EMQX 把无人接收的 QoS 0 回执计入丢弃（4,161 条），守恒判定误报；改为订阅后为 0。

### 4.2 命令

```bash
python ladder.py run --plan 10000 --hold 1800 --mix 60:0.7,15:0.25,1:0.05 --points 30 --id-ratio 0.5 --per-process 2500 --out results-m4-1万-30min
python ladder.py run --plan 25000 --hold 1800 --mix 60:0.7,15:0.25,1:0.05 --points 30 --id-ratio 0.5 --per-process 2500 --out results-m4-2.5万-30min
python ladder.py run --plan 10000 --hold 7200 --mix 60:0.7,15:0.25,1:0.05 --points 30 --id-ratio 0.5 --per-process 2500 --out results-m4-1万-浸泡2h
```

14:09:51 开始，17:21:29 结束，档间间隔 2 分钟。另起线程每 5 分钟采样应用主机各容器、Redis 内存与流长度、InfluxDB 数据目录。

### 4.3 每档判定

| 档位 | 掉线 | 首次被拒 | 积压峰值 | 发压进程 最忙单核 / 合计 | 宿主机 CPU 平均 / 峰值（VMware） | 宿主机最低可用内存 |
|---|---|---|---|---|---|---|
| 1 万 30 分钟 | 0 | 0 | 5,463 | 44% / 1.7 核 | 21% / 47%（8%） | 1,523 MB |
| 2.5 万 30 分钟 | 0 | 0 | 61,465 | 62% / 5.7 核 | 49% / 100%（18%） | 212 MB |
| 1 万 2 小时 | 0 | 0 | 1,075 | 48% / 1.8 核 | 26% / 100%（9%） | 48 MB |

- 2.5 万档的积压峰值 6.1 万出现在 2.5 万台集中建连的阶段；稳态中总线积压约 2,200 条，远低于 5 秒流量（约 9,800 条）。
- 浸泡档宿主机 CPU 峰值 100%、可用内存最低 48 MB，是宿主机上的瞬时情况，平均值均在可信线内；判据只看平均值，本次照实记录。

### 4.4 浸泡期间的趋势

Prometheus 回读（每档稳态开始 5 分钟后、中点、结束前 1 分钟）：

| 档位 | EMQX 主机已用内存 GB（占比） | server 堆 MB | 总线 lag + pending | transport 会话队列 |
|---|---|---|---|---|
| 1 万 30 分钟 | 2.16 → 2.13 → 2.12（26%） | 174 → 250 → 202 | 约 1,030～1,040 | 0 |
| 2.5 万 30 分钟 | 2.51 → 2.55 → 2.58（31%） | 180 → 233 → 253 | 约 2,170～2,230 | 0 |
| 1 万 2 小时 | 2.29 → 2.12 → 2.11（25%） | 294 → 298 → 323 | 约 1,020～1,050 | 0 |

5 分钟采样（应用主机）：

- **server 容器**：内存稳定在 1.29 GiB，上限 1.465 GiB，与堆内存的波动无关，是 JVM 预留。浸泡 2 小时内没有变化。
- **InfluxDB 容器**：1.1～1.7 GiB 之间波动，上限 2 GiB。峰值 1.733 GiB 出现在 2.5 万档，占上限 87%；浸泡期间在 1.1～1.5 GiB 之间，无上升趋势。
- **Redis**：`used_memory` 由 276 MB 涨到约 830 MB 后持平。原因是 30 测点的报文更大，上行流长度一直在 `MAXLEN` 100 万条上限附近（1,000,000～1,000,017）。
  - 浸泡中 15:30 有一次 CPU 107% 的采样，内存无变化。
- **InfluxDB 数据目录**：parquet 文件由 986 个增到 1,006 个，目录由 3.0 GB 增到 3.8 GB（约 3 小时）。数据量的增长符合预期；30 天的保留与 `INFLUXDB3_QUERY_FILE_LIMIT` 的余量不受影响。
- **应用主机整机**：`free` 的已用内存在 5.5～6.3 GB 之间，共 11.4 GB，浸泡期间无上升趋势。

结论：2 小时浸泡中 EMQX、server、Redis、InfluxDB 的内存与总线积压都没有随时间持续上涨，满足计划中「内存不持续上涨」的要求。

### 4.5 采样缺陷

`m4` 采样脚本中 EMQX 主机的 `docker stats --format` 模板写错，花括号转义多了一层，导致 5 分钟采样中 EMQX 一行全部是 `template parsing error`。EMQX 侧的趋势改用上表的 Prometheus 回读，即 transport 上报的 EMQX 节点内存。EMQX 容器自身的 RSS 本次没有记录。

## 5. 风险与观察

1. **InfluxDB 内存余量**：2.5 万档峰值占上限 87%。设备数或测点数再往上时，可能先撞上 InfluxDB 的 2 GiB `mem_limit`。下一次提高档位时要盯这一项。
2. **Redis 内存与报文大小**：Redis 内存约等于 100 万条流条目乘以每条报文大小。30 测点时约 0.8 GB；测点更多时会线性增长。
3. **本机发压上限**：5 万连接需要发压端约 13.4 核，宿主机平均 CPU 被推到 89%。本机可信的连接规模约为 2.5 万。要测更多连接，需要第二台发压机或独立服务器（`--shard`）。
4. **新增列**：压测产品新增约 22 个测点，`property` 表随之增加约 22 列。所有者已于 2026-11-13 确认接受。
