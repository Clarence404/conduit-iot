# Conduit IoT 生产级 IoT SaaS Roadmap

- 日期：2026-10-20
- 状态：当前生效
- 产品目标：建设面向工业、能源、园区与设备运营场景的生产级多租户 IoT SaaS 平台；核心能力对标 ThingsBoard，但不以逐项复制为目标。
- 能力声明：本文描述目标与计划，生产就绪状态以各阶段验收和测试报告为准；当前已实现能力见第 2 节。

## 1. 产品边界

Conduit 的核心价值是可靠设备接入、统一物模型、实时数据处理、设备运营与多租户服务。平台同时支持公有 SaaS、客户独立部署和边缘节点接入，三种形态共享核心领域模型与协议，不维护三套产品。

近期不自建通用低代码平台、消息中间件或支付系统；优先把 IoT 控制面、数据面、租户治理和可运营能力做完整。与 ThingsBoard 的竞争应聚焦于更清晰的产品模型、更可靠的上报语义、更低的部署复杂度和更适合国内工业场景的交付体验。

## 2. 当前基线与关键差距

当前 V0.2 已具备 MQTT 接入、设备鉴权、物模型、多租户基础、最新值与历史曲线、可靠上报、双 Transport 单活多备、演示资产和完整容器部署。

2026-10-26 实施更新：B1 组织模型/界面已交付；B2 已补充五个预置角色、自定义角色、租户/项目/站点绑定、SQL 范围、用户资源权限配置与项目成员委派。B3 身份治理、B4 持久化审计仍未完成。授权发布采用 shadow → enforce，故障保护为保留范围的 read-only，详见 [授权说明](authorization.md)。新增功能必须配套可复现演示数据和测试报告。

距离生产级 SaaS 仍有六类关键差距：

1. 租户隔离以 MyBatis-Plus 强制过滤、租户组合外键和受控系统通道为基础；项目/站点细粒度权限已开始交付，数据库直连隔离、配额和资源治理仍有缺口。
2. 缺少租户注册、邀请、套餐、用量计量、账单和生命周期管理，尚未形成 SaaS 商业闭环。
3. 缺少 RPC、设备影子、属性同步、网关/子设备、OTA 和完整凭据生命周期。
4. 缺少可配置规则引擎、告警闭环、通知升级、仪表盘与资产关系模型。
5. 部署仍以单机 Compose 为主，缺少水平扩展、滚动升级、备份恢复、灾备演练和容量 SLO。
6. 开放 API、Webhook、数据转发、连接器 SDK、审计与企业身份集成尚不完整。

## 3. 路线原则

- 先安全边界与平台治理，再增加业务功能；任何新数据模型必须先定义租户归属、权限、配额和审计。
- 控制面与数据面逐步解耦；设备接入、消息处理、查询和管理 API 可以独立扩缩容。
- 租户隔离同时覆盖访问安全、运行资源和故障影响范围；共享部署先行，提前定义租户到区域、集群和存储位置的映射，支持后续专属资源与租户迁移。
- 从 V0.3 起持续交付租户生命周期、用量采集、基础可观测、发布与恢复能力；V0.8 深化集群高可用，V0.9 完成计费与商业运营。
- 所有异步处理都要可重放、幂等、可观测；所有外部调用都要有超时、重试、熔断和死信策略。
- SaaS 与独立部署使用同一代码基线，通过能力开关、部署拓扑和许可证/套餐控制差异。
- 演示数据不得进入生产租户。V4 历史迁移保持不可变，但在首次正式生产发布前建立无演示种子的生产基线；开发和演示数据改由显式 profile 或初始化任务创建。
- 每阶段必须同时交付功能、迁移/回滚方案、容量指标、监控、审计、安全测试和运维文档。

## 4. 分阶段 Roadmap

### V0.3：SaaS 基座与安全边界

- 租户上下文全链路强制传播：REST、MQTT、Redis Streams、定时任务、缓存和时序查询均不可缺失 tenant id。
- PostgreSQL 行级安全或等价的数据库强制隔离；补齐组合唯一键、外键、租户级索引和跨租户自动化攻击测试。
- RBAC 2.0：平台、租户、项目/空间三级角色，自定义角色与权限集合；用户邀请、禁用、会话吊销、密码策略和 MFA 预留。
- 明确租户、客户、项目、站点与资产的关系：租户是安全与资源边界，客户是租户内业务对象；定义用户成员关系、设备归属、权限继承和跨项目授权，V0.6 再交付完整业务界面。
- 租户配额：设备数、用户数、消息速率、存储保留期、API 频率；超限行为明确且可审计。
- 租户资源治理：租户级逻辑队列或等价调度隔离、公平调度、积压上限、查询时间/扫描量/并发预算；设备重连与离线补传限速、指数退避与抖动；明确限流反馈、重试和降级行为。
- SaaS 控制面：租户创建、资源分配、暂停、恢复、注销使用可重试、幂等且可审计的状态机；保留区域/集群/存储路由字段，明确暂停时接入、查询、任务与数据保留行为。
- 用量基础：定义设备、消息、存储和查询的计量事件、计量单位、去重键和时间窗口；区分原始上报、重传、有效处理与拒绝消息，建立租户用量和成本观测，后续能力接入同一口径。
- 全量审计日志、操作人/代入人追踪、导出与保留策略。
- 工程基线：CI/CD、版本化构建产物、配置与密钥校验、依赖扫描、迁移兼容检查、发布追踪；数据库变更采用向后兼容的扩展—迁移—收缩流程，分别定义应用回滚与数据恢复。
- 运维基线：服务与租户维度指标、队列积压/最老消息年龄、处理延迟和错误告警；制定各存储的备份与恢复步骤，在隔离环境验证恢复，并记录实测恢复点与耗时。
- 把演示数据从生产初始化链路剥离，建立 production / demo 两套明确启动模式。

**历史数据语义（2026-10-26）**：全局明确遥测 null/测点缺省表示该时刻没有上报、0表示有效零值；缺测不得补零，已知曲线缺口须断线。先明确聚合缺桶、波动带、最新值与导出的语义，原始历史缺口识别需定义采样周期/缺测阈值。规则及静态审查见 [遥测值约定](telemetry-value-semantics.md)。

**历史查询修复（2026-10-26 用户要求暂停）**：VM 的 7 天历史查询触发 InfluxDB 文件扫描上限（432 个 Parquet 文件）。恢复后处理有界、可配置的 `--query-file-limit` 调整及容量验证，同时修正扫描超限错误分类和失败后旧曲线的时间范围标记；长范围分段查询纳入 V0.3-E，先定义超时、并发、扫描预算和聚合合并语义。详见 [实施计划](superpowers/plans/2026-10-26-history-query-limits.md)。尚未调整参数，不表示当前已恢复 7/30 天查询。

**PostgreSQL 行级安全（RLS）不实施，降级为可选增强（2026-10-22 决定）**：V0.3-A 原定以 RLS 或等价的数据库强制隔离为主体，评估后改为维持「`tenant_id` 列 + MyBatis-Plus 租户拦截器」的应用层方案，并缩减 A 的范围为一次性加固（见上表与对应 spec）。取舍是明确的：隔离保证全部留在应用层，不经过 MyBatis 的原生 JDBC、将来替换 ORM 或引入不走拦截器的组件、数据库工具直连，数据库都不会替应用拦截。核实后确认 Redis 与 InfluxDB 当前没有独立暴露面（全部访问都先经受租户过滤的 PostgreSQL 查询取得设备，`device_key` 全局唯一），因此也不给 Redis 键加租户前缀，改为把该前提固化为约定并用测试守住。重新评估的触发条件：出现一条真实的跨租户数据泄露；引入不经过 MyBatis 的数据访问路径；多人协作开发或业务表超过 10 张。RLS 是纯叠加能力，届时实施不会使本次产出返工。

**CI 暂不做（2026-10-21 决定）**：评估后认为对当前形态收益有限——没有团队协作，没有外部使用者消费构建产物，而合并前的全量测试目前已由流程保证。唯一真实缺口是曾有本地配置连同口令被提交进公开仓库，但不足以单独支撑一套 CI 的建设与维护成本。遇到「本该拦住却没拦住」的情况时重新评估，届时优先做最便宜的一层：提交密钥扫描、前端测试与类型检查、后端单元测试（不含 Testcontainers 集成测试与 e2e）。

完成门槛：跨租户用例覆盖 API、消息、缓存和查询；高负载租户与正常租户混合压测时，正常租户达到 spec 预先约定的延迟和错误率预算；租户生命周期故障后可续跑且不重复分配资源；用量可对账，备份可恢复，发布可追溯；生产模式启动后没有演示租户或设备。验收须留存测试报告，安全测试通过不等于对所有攻击路径的绝对证明。

### V0.4：设备生命周期与控制

- 设备批量注册、导入、分组、标签、凭据轮换/吊销、证书认证和设备模板。
- 设备开通定义出厂身份、首次认领、租户绑定、重复认领防护与退役流程；模板统一关联协议、物模型版本、配置及固件兼容要求。
- 客户端属性、服务端属性、共享属性与设备影子，带版本号和冲突策略。
- 双向 RPC：请求、设备回执、超时、重试、取消和完整状态查询。
- 网关与子设备模型，支持网关代认证、代上报和子设备上下线。
- OTA 任务基础：包管理、灰度批次、进度、失败回滚与审计。
- 统一批量任务中心，供 RPC、配置下发、OTA 和凭据轮换复用：目标快照/动态组、任务与单设备执行状态、幂等键、并发与速率限制、维护窗口、灰度放量、超时/重试、取消和失败阈值自动中止。
- 控制指令定义有效期、重复执行保护与离线策略，区分已发送、已接收、已执行和结果未知；取消或超时不能推断设备未执行，自动重试必须符合指令幂等性。固件包验证签名与完整性，回滚依赖设备能力声明。

完成门槛：设备从入网、运行、控制、轮换凭据到退役的全过程可管理和追溯；批量任务支持故障恢复、灰度与阈值中止，并验证重复投递、设备离线、结果丢失和不支持回滚的设备场景。

### V0.5：规则引擎与告警中心

- 计算字段、事件模型和规则 DSL；后续演进为可视化 DAG，不直接开放任意脚本执行。
- 规则节点支持过滤、转换、聚合、阈值、持续时间、离线、去抖、关联和定时触发。
- 告警产生、升级、确认、指派、恢复、关闭和评论时间线。
- Webhook、邮件及可插拔通知通道；重试、签名、限流、熔断和死信可观测。
- 规则版本、草稿/发布、回滚、模拟执行和测试样本。
- 数据治理与规则语义：物模型版本、兼容变更和历史解析绑定；统一单位、精度、质量标记及设备时间/平台接收时间。定义去重范围与有效期、乱序/迟到窗口、聚合修正和补传是否触发告警；重放默认禁止再次发送通知或控制指令，显式授权后才允许产生副作用。

完成门槛：租户无需发版即可配置常见规则；规则失败不阻塞主数据链路，且可以定位、重放和审计；以重复、乱序、迟到、时钟偏差和物模型升级样本验证结果及副作用符合约定。

### V0.6：资产、仪表盘与运营工作台

- 资产树、关系图、客户/项目/站点模型，支持设备与资产多维关联。
- 仪表盘、组件库、变量、时间范围、权限、模板、分享和大屏模式。
- 告警工作台、设备运营视图、批量操作、报表计划与 CSV/Excel 导出。
- 移动端自适应和面向最终客户的只读门户。
- 数据生命周期：租户级保留期、降采样、冷热归档、导出与可追溯删除；对关系库、时序库、缓存、对象存储和备份明确删除时限及恢复后再次删除的机制。数据量与保留期变化纳入配额和成本评估。

完成门槛：租户可独立完成“建资产—接设备—配规则—做看板—处理告警”的完整业务闭环。

### V0.7：开放平台与集成生态

- 版本化 OpenAPI、AccessKey/OAuth2、作用域、签名、限流、幂等键和调用审计。
- Webhook、MQTT/Kafka 数据转发、数据库/对象存储落地和常见云服务连接器。
- 协议适配器与规则节点 SDK，提供兼容性测试套件和示例工程。
- 租户配置、物模型、规则、仪表盘和资产的导入导出与环境迁移。
- 连接器、规则节点和公开接口声明版本兼容与资源预算；集成凭据按租户隔离并可轮换，Webhook 出站地址执行网络访问限制，扩展组件故障不得耗尽核心处理资源。

完成门槛：第三方系统可以只通过公开接口完成租户内主要操作，新连接器不修改核心服务。

### V0.8：云原生、高可用与安全合规

- Kubernetes/Helm 部署、无状态服务水平扩展、滚动升级、优雅停机和自动伸缩。
- 评估并落地可水平扩展的消息与时序存储方案；去除单活 Transport 的吞吐上限。
- PostgreSQL、缓存、消息和时序数据的备份恢复、RPO/RTO、跨可用区部署和灾备演练。
- OpenTelemetry、指标/日志/追踪、租户级用量观测、SLO 和告警值班体系。
- 威胁建模、依赖与镜像扫描、密钥托管、TLS/mTLS、数据加密、渗透测试和隐私合规基线。
- 在 V0.3 路由模型上实现共享资源与专属资源部署档位、租户迁移和故障域划分；迁移需校验数据完整性、路由切换及回退能力。

完成门槛：在参考集群上完成滚动升级、节点故障、存储恢复和 30 天稳定性测试，达到公开的 SLO。

### V0.9：商业化 SaaS

- 在 V0.3 租户控制面上增加自助注册、试用、套餐和功能权益；开通流程复用已有生命周期状态机。
- 在 V0.3 计量基础上补齐规则执行、API 和通知等用量，形成可追溯、可重算的计费账本与对账流程，明确迟到事件、重复事件和套餐变更的结算规则。
- 订阅、账单、优惠、欠费策略和支付渠道适配层；不在核心域硬编码单一支付厂商。
- 平台运营后台、客户支持代入审批、公告、工单集成、租户迁移和数据删除流程。
- 白标基础：品牌、域名、邮件模板和登录页配置。

完成门槛：新客户可以自助完成注册、试用、升级、用量查看和续费，平台方可以运营并审计全过程。

### V1.0：SaaS GA

- 冻结兼容性策略、API 生命周期、数据库升级/回滚和支持周期。
- 建立明确的参考容量档位；待验证目标为单集群 100 个活跃租户、10 万注册设备、2 万并发连接、持续 5,000 条消息/秒。这些数值不是当前能力声明，最终以容量模型和压测报告为准。
- 容量报告必须固定硬件与拓扑、消息大小/测点数、上报频率与可靠模式占比、租户流量分布、保留期、规则复杂度及并发查询；分别报告稳态、突发、重连与补传时的吞吐、积压恢复时间、P95/P99 延迟和错误率。
- 核心链路可用性待验证目标不低于 99.9%；在正式商用前定义按自然月统计的 SLI、观测点、成功/失败条件和维护窗口口径，分别衡量管理 API、接入持久确认、端到端入库与查询，明确数据新鲜度和错误预算；不把接收回执当作入库成功。
- 租户越权为发布阻断项，已发现问题修复并复验后才能发布；RPO/RTO 按服务档位和存储类型定义，并由恢复演练报告验证。
- 发布运维手册、管理员手册、设备接入 SDK、迁移指南、安全白皮书和服务状态页。

完成门槛：设计伙伴在真实业务中连续运行至少 30 天，通过安全、容量、计费准确性和灾备验收后再开放正式商用。

## 5. V1.x 与 V2 方向

- V1.1：HTTP、CoAP、LwM2M、Modbus TCP/RTU、OPC UA 等协议与边缘网关。
- V1.2：规模提升到多集群和十万级并发连接，支持数据分层、冷热存储和区域部署。
- V1.3：企业能力，包括 SSO/SAML/OIDC、SCIM、审批流、专属实例和更细粒度数据权限。
- V2.0：多区域 SaaS、边云协同、应用市场、白标与合作伙伴体系。
- V2.1：受控 AI 能力，包括自然语言查询、异常检测、物模型草稿和告警归因；AI 不能绕过租户权限和审计。

## 6. 最近三个实施里程碑

1. V0.3-A 生产初始化与租户隔离：生产基线剥离演示种子、数据库强隔离、租户/客户/项目边界及路由模型；建立 CI/CD、基础指标与备份恢复基线，执行跨租户安全验证。
2. V0.3-B 租户治理与运营基础：IAM、审计、生命周期状态机、配额、公平调度、查询预算和用量采集；以混合租户负载验证隔离和成本口径。功能过大时继续拆分 spec，以上能力完成后再通过 V0.3 验收。
3. V0.4-A 设备生命周期与任务基础：批量注册、凭据轮换、属性/影子、RPC 及统一任务状态机最小闭环，为后续 OTA 和配置灰度提供基础。

每个里程碑启动前单独编写 spec，并明确数据迁移、回滚、容量、安全和验收方案。
