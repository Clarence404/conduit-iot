# 验证报告：EMQX 直写 Kafka 能否替代 transport（2026-11-17）

**测试类型**：技术验证（spike），包含故障注入的压力测试，以及与 transport 方案的回归对比。
**计划**：[`2026-11-17-emqx-kafka-sink-spike.md`](../superpowers/plans/2026-11-17-emqx-kafka-sink-spike.md)

## 结论

**可行，但有一项必须先解决：Kafka 中断恢复后会产生大量重复写入。** 建议按「去掉 transport」写正式 spec，前提是先解决重复放大问题，并按第 5 节的条件设计。

1. **正常运行、Kafka 变慢、吞吐、补传洪峰都没有丢数，表现不比 transport 方案差。**
   - 基线、暂停 Kafka 60 秒、30 测点逐档提速到 12,000 条/秒、2.5 万台断网 5 分钟后同时补传，PUBACK 与 Kafka 条数全部守恒，EMQX 动作的 `failed` 和 `dropped` 都是 0。
   - 同一个补传洪峰场景，transport 方案修正前少了 25 万条，修正后才守恒；直写 Kafka 一次就守恒，p99 3.4 秒。
2. **Kafka 停机 60 秒期间也不丢，但恢复后重复非常严重。**
   - 缩小版复现（500 台、停 Kafka 60 秒、内存缓冲）：PUBACK 74,999 条，Kafka 中实际 744,563 条，**去重后恰好 74,999 条**。同一条消息最多被写了 22 次，总量约为 10 倍。
   - 原场景（2,000 台）：内存缓冲约 10 倍，磁盘缓冲约 5.6 倍。
   - 下游按（设备, ts）幂等写入，所以数据本身不会错，但恢复瞬间 Kafka 和消费端会承受几倍的放大流量。原因可能是 EMQX 的 Kafka 生产者重连后反复重发整批缓冲，**还没定位到具体原因和调参办法**。
3. **EMQX 进程被强杀时，缓冲里的消息会丢：内存缓冲整批丢，磁盘缓冲也丢一小部分。**
   - Kafka 停机期间强杀 EMQX：内存缓冲少 59,925 条，磁盘缓冲少 3,250 条（约占 2%）。
   - 这一点**并不比 transport 方案差**。设备收到的 PUBACK 在两种方案里都是 EMQX 收到消息就回的；transport 的「写进总线才确认」只针对 EMQX 到 transport 这一跳。EMQX 崩溃时，已确认但还在 EMQX 里的消息两种方案都会丢（transport 方案的实测见 `durability-validation.md`：500 条最多丢 142 条），都要靠设备带 `id` 重发兜底。
4. **PUBACK 的时机**：EMQX 收到消息就回 PUBACK，不等 Kafka 确认。Kafka 停机期间设备照常收到确认，掉线和错误都是 0。

## 1. 环境

- 129 上的独立 compose 项目 `/opt/emqx-kafka-spike`，不影响拆分部署：
  - `emqx/emqx:5.10.5`：自带 `emqx_bridge_kafka`，内置社区 License（单节点，`max_sessions` 1000 万，到 2029-03-01），不鉴权；
  - `bitnamilegacy/kafka:4.0`：单节点 KRaft，堆 1 GB；主题 `conduit-up`，16 个分区，单副本。
- EMQX 规则 `SELECT * FROM "conduit/+/+/up/#"` 直接交给 Kafka 动作。动作配置：key 为 `${clientid}`（`key_dispatch`），`required_acks = all_isr`，`query_mode = async`；缓冲模式按场景切换（memory / disk），每分区上限 2 GB。
- 发压：`loadgen.py` 的 fleet 模式，环境变量指向验证环境；`id-ratio` 为 0，因为验证环境没有业务回执。
- 计数：Kafka 主题各分区 end offset 之和的增量，与客户端 PUBACK 数比较；同时记录 EMQX 动作指标（matched / success / failed / dropped / retried）。
- 驱动脚本放在 scratchpad，没有入库；用到的 `loadgen.py` 是仓库当前版本。

**说明**
- S4 中 EMQX 重启后动作指标归零，所以那两行动作增量显示为 0，以 Kafka 条数为准。强杀期间 2,000 台设备全部掉线，发压器不自动重连，后续发送都记为客户端错误；判定只比较已收到 PUBACK 的部分。
- S5 只衡量 EMQX → Kafka 这一段，不含 server 消费与写 InfluxDB，**不能直接和 transport 方案的端到端吞吐对比**。
- 缩小版 S1 是先删掉主题重建、清空之后跑的，结束后从头读出全部消息，对「key + 报文」整体去重。报文里带每台设备唯一的 ts，所以去重后的条数就是不同消息的条数。

## 3. 计划中问题的回答

1. **PUBACK 的时机**：EMQX 收到消息即回 PUBACK，不等 Kafka 确认。在这一点上，两种方案对设备的语义完全相同。
2. **Kafka 不可用或变慢**：消息在 EMQX 动作缓冲里排队，60 秒内不丢，内存与磁盘缓冲都一样；恢复后会出现几倍的重复写入，重复原因待查。缓冲上限设为每分区 2 GB，本次没有压到满，满了之后的丢弃行为没测。
3. **强杀 EMQX**：内存缓冲全部丢失；磁盘缓冲大部分能恢复，但仍丢约 2%，原因可能是最后一段缓冲还没落盘。两种方案都要靠设备带 `id` 重发兜底。
4. **补传洪峰与吞吐**：S6 补传洪峰守恒，S5 在 12,000 条/秒时仍守恒，EMQX 直写 Kafka 这一段没有出现瓶颈。
5. **顺序与分区**：按 `clientid` 分区，同一设备固定落在同一个分区。逐条顺序没有专门核对；重复写入时同一条消息会出现多次，消费端仍需按（设备, ts）做幂等。
6. **业务回执**：去掉 transport 后，只能由 server 消费 Kafka 之后发回执。可以通过 EMQX HTTP 发布接口，或 server 自己维护一个 MQTT 发布连接。回执的含义也会变强，从「平台已持久接收」变成「已入库」。本次没有实现。

## 4. 两种方案对比

| | transport 方案（现状，内部监听器 + 单活） | EMQX 直写 Kafka |
|---|---|---|
| 设备收到 PUBACK 的含义 | EMQX 已收到 | 相同 |
| EMQX 崩溃 | 会话队列中未投递的消息丢失 | 动作缓冲丢失（磁盘缓冲丢得少） |
| 下游中断 | 排在 EMQX 会话队列里（每连接 10 万条，内存） | 排在动作缓冲里（可落盘，上限可配到 GB 级） |
| 补传洪峰 | 修正后守恒，需要内部监听器与 zone | 一次守恒 |
| 横向扩展 | 需要做身份池多活 | 由 EMQX 集群负责（商业版） |
| 总线保留期 | Redis 内存，100 万条上限 | Kafka 磁盘，按时间保留 |
| 组件数 | 多一个 transport，还要 Redis 选主 | 少一层，但多一个 Kafka |
| 业务回执 | transport 写入后发 | 需要 server 入库后再发（新开发） |
| 已知问题 | 单活、历史包袱 | Kafka 中断恢复后重复放大 |

## 5. 若去掉 transport，正式设计必须包含

1. **查清并压住重复放大**：查 EMQX Kafka 生产者的重试与批量参数，以及 EMQX 的已知问题；目标是恢复后的重复不超过 1 倍。查不清的话，消费端要能承受数倍的瞬时流量。
2. **使用磁盘缓冲**，并按「可容忍 Kafka 停多久 × 峰值速率」设置缓冲上限，同时测出缓冲写满后的行为。
3. **server 改为消费 Kafka**：替换 `MessageBus` 实现，消费者组按分区分配，保持写入幂等。
4. **业务回执由 server 发出**，并相应更新设备接入文档里回执的含义。
5. **e2e 重做**：杀 server、停 Kafka、强杀 EMQX、补传洪峰；吞吐按端到端（含 server 写 InfluxDB）重测。
6. **非 MQTT 协议**（HTTP、Modbus 等）以后需要单独的接入服务，直接写 Kafka。

## 6. 跳过、阻塞与遗留

- 重复放大的原因没有定位，调参没有尝试。
- 动作缓冲写满之后的行为没测。
- 业务回执由 server 发出的方案没有实现，只做了评估。
- 吞吐只测了 EMQX → Kafka 这一段。
- 本次测试中，为结束卡住的驱动进程，曾执行过一条按窗口标题批量结束进程的命令（`taskkill /FI "WINDOWTITLE eq *"`）。核对后确认没有生效，用户的程序都还在运行；实际被结束的只有两个卡住的 Python 进程。以后不再使用这类批量结束命令。
- 验证环境 `/opt/emqx-kafka-spike` 仍在 129 上运行，主题里有数据。之后停掉还是保留，由所有者决定。
- 结果 JSON 在 scratchpad 的 `spike/results/`，没有入库。
