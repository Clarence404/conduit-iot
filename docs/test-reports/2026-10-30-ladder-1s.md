# 2026-10-30 每台每秒 1 条的设备数阶梯（拆分部署）

## 被测范围与代码状态

- 代码 `e273517`（`ladder.py` 首次正式使用）；拆分部署：EMQX 单独一台 VM（vmxnet3，容量参数取 EMQX 接受的最大值），其余服务在压测 VM。
- 发压：`ladder.py run --plan 2000,5000,8000,10000,12000,15000,18000,20000 --rate 1 --hold 300`，单台发压机（与两台 VM 同一物理机），每进程 1,000 台。

## 测试类型

容量测试（守恒判据 + 掉线、p99 ≤ 1 秒、积压、EMQX 强杀与过载告警，判据见 `docs/script/loadtest/README.md`）。首个不合格档位即停。

|---|---|---|---|---|---|---|---|---|---|
| 2,000 | ✅ | 599,982 = 599,982 | 2,014 | 0 | 2.1 / 8.0 / 15.5 | 20% / 24% | 1.75 核 | 2 | 980 / 27 ms |
| 5,000 | ❌ | 1,402,041 = 1,402,041 | 4,661 | 403 | 4.4 / 227 / 3,345 | 54% / 93% | 3.71 核 | 7,193 | 1,108 / 254 ms |

5,000 档：开压约 1 分钟后 EMQX 告警 `runq_overload`（运行队列 1,498，持续 22 秒），同期 transport 连接信箱冲到 7,193、403 台设备掉线、
p99 升到 3.3 秒；EMQX 实收 4,678 条/秒（未达 5,000）。已确认的消息全部入库（守恒成立），丢弃与死信为 0。应用主机只用 3.7 核、
无 steal，流水线每批约 1.1 秒（等 WAL 刷盘），不是瓶颈。

## 分析

- **瓶颈在 EMQX 所在主机**，且出现在 CPU 峰值（93%）而非平均值（54%）：大批连接同时活跃时 EMQX 调度跟不上，过载告警、信箱堆积、
  PUBACK 变慢、部分连接保活超时被断。
- **连接数才是成本**：EMQX 每条消息的 CPU 约 0.9 毫秒（4.3 核 / 4,678 条/秒），而 2026-10-29 单机 600 条连接各发高频时约 0.24 毫秒——
  每台设备各占一条连接、每条消息单独一次网络往返，比少量连接批量发送贵数倍。因此不能用「600 连接 11,500 条/秒」推算设备数。
- 发压机与两台 VM 同在一台物理机，EMQX VM 的 8 核并非独占；能否把 5,000 推高需分机发压验证。

## 掉线原因分析（复现，14:32～14:36）

同样 5,000 台 × 每秒 1 条、180 秒，加诊断：客户端记录每台掉线的原因与各发压进程事件循环的最长停顿；Windows 宿主机每 2 秒采 CPU
与可用内存（`typeperf`）；EMQX 日志临时调到 info 以记录每条连接的终止原因（结束后已恢复 warning）。

| 项目 | 结果 |
|---|---|
| 客户端 | 发出 899,947，确认 899,927，掉线 1 台；p99 2,779 ms、最大 13,396 ms |
| 发压进程事件循环最长停顿 | 0.40～1.04 秒（5 个进程）——发压端没有卡住 |
| **Windows 宿主机 CPU** | **平均 83%、峰值 100%**（几乎全程 > 80%）；可用内存最低 504 MB |
| EMQX | 14:35:16 告警 `runq_overload`（运行队列 152），持续 45 秒 |
| 掉线那条连接 | EMQX：`terminate ... reason: {shutdown,tcp_closed}`（对端关闭）；客户端：`Unspecified error`（连接丢失）。未出现 `send_timeout` |

**结论：掉线与秒级时延的根因是物理机 CPU 饱和。** 发压程序与两台 VM 同在一台 20 核宿主机上，5,000 条/秒时宿主机 CPU 打满，
EMQX 所在 VM 拿不到物理 CPU，调度队列过载（`runq_overload`），PUBACK 延迟到数秒。双方都认为是对方关闭了连接、EMQX 也没有触发
15 秒发送超时，推断是 EMQX VM 长时间未响应 TCP，宿主机协议栈重传放弃后重置了连接（未抓包证实）。

排除项：发压端自身停顿（最长 1 秒）、EMQX 发送超时强制断开（无 `send_timeout`，且客户端最大等待 16 秒以内）、MQTT 保活超时
（60 秒，远大于观测到的停顿）、鉴权（全部一次通过）、应用主机（3.7 核，无积压）。

**因此本轮的 2,000 / 5,000 结论反映的是这台物理机的上限，不是平台的上限。** 下一步须把发压程序放到另一台电脑（`ladder.py` 已支持多机），
或减少宿主机上的其他负载后再测。
