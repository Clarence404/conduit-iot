# EMQX 网络对照与6500台设备上探：最终报告

- 日期：2026-11-02，Asia/Shanghai；结束复核约22:36。
- 范围：拆分部署，设备每秒1条，QoS 1，复用已有压测产品/设备，未重置密钥。
- Git：`codex/emqx-host-network`；本轮部署与工具改动未提交/推送。期间其他文档提交推进至`811e441`，未覆盖其内容。
- 测试类型：网络配置A/B回归与容量向上探测；不是长时间浸泡或最大容量认证。
- 环境：Windows发压机，8 vCPU EMQX VM、8 vCPU应用VM；同一物理机，镜像与设备集保持一致。

## 已得结论

1. bridge下6000台×每秒1条，三轮300秒均通过当前阶梯判据。
2. host下三轮仅一轮通过，没有可重复的性能收益；保留bridge，不推荐切换host。
3. bridge下6500台×每秒1条，首轮300秒通过。尚未重复、未测更高档位，不能称其为稳定容量上限。
4. 11月1日6000台起失败在本轮bridge下未复现，说明旧阈值受运行环境影响，不应作为固定的平台极限。

```bash
python -X utf8 -u docs/script/loadtest/network_ab.py --bridge-only --repeats 1 --hold 300 --levels 6500
```

本地忽略目录 `docs/script/loadtest/results/` 中：

- `network-ab-20261102-194928/`：首轮bridge→host，各300秒。
- `network-ab-20261102-215950/`：host→bridge→bridge→host，各300秒；包含每档事件日志和CPU/网卡前后快照。
- `network-ab-20261102-222815/`：6500台bridge，300秒。

每档有发压JSON和`summary.md`。工具的设备鉴权、断连、确认延迟、InfluxDB实际行数、

TPS是既有脚本的Prometheus窗口估计值，不等于简单的行数除以300；延迟为设备PUBACK，不是业务入库延迟。

## 可比性与瓶颈判断

后两次bridge与末次host的发压机平均CPU分别46.0%、46.5%、45.9%，应用VM约37%，EMQX主机约50%～52%，
说明host不天然较慢；问题是本组试验没有显示其收益稳定。
host第二轮告警日志已在重建前保存，类型为两条transport连接拥塞、`runq_overload`与`high_cpu_usage`。
bridge两次重复与末次host事件日志均无匹配告警。首轮host仅有计数，未保留原日志，不能补猜其类型。

前后`/proc/stat`快照含建连、排空与查询，不称为纯稳态CPU剖析；本轮没有连续的稳态分核采样。
三次重复没有随机化测试次序、没有显著性检验，同物理机其他进程与VM争用仍是混杂因素。
因此本报告否决的是“当前证据足以推荐host优化”，不证明host网络普遍劣于bridge。

## 故障、无效尝试和恢复

- VM未启动导致SSH超时；用户授权后用VMware后台启动，应用网卡RX=4096在重启后确认保留。
- InfluxDB因四个零字节WAL文件反复重启，首次续测无法排空基线。停库核对后移到数据卷
  `recovery/empty-wal-20261102/`，不删除有效WAL，恢复后healthy且重启0。
  不据此声称关机前历史数据完整；该故障期间的尝试没有计入通过结果。
- 既有ladder输出✅时遇到GBK编码错误，驱动已给自身和子进程统一UTF-8；后续实际报告成功输出。
- 20:39后台重复尝试因连续非测试CPU高于15%而中止，`network-ab-20261102-203949/`保留中止标记；不计通过/失败。
- 所有完整试验结束均恢复bridge及原先运行的8个其他容器、模拟器。22:36独立复查EMQX bridge/healthy、
  InfluxDB healthy/RestartCount=0、其他容器运行，无遗留发压进程。
