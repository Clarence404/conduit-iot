# 流水线入库瓶颈定位：每条消息两次 Redis 网络往返

- 日期：2026-10-28（Asia/Shanghai）
- 被测版本：`ae96be1`
- 环境：压测机 192.168.126.129，standalone 栈 + 监控栈，600 台压测设备
- 结论：**入库 TPS 的上限由「每条消息 2 次串行 Redis 网络往返」决定**，约 3,000 条/秒。InfluxDB、JVM 堆与 GC、Redis 刷盘策略均已排除。

## 1. 现象

端到端三段速率（6000 条/秒过载）：

| 阶段 | 峰值 |
|---|---|
| 接入（EMQX 接收并 PUBACK） | 8,881 条/秒 |
| 投递（EMQX → transport → Redis 总线） | 5,110 条/秒 |
| **入库（写进 InfluxDB）** | **2,943 条/秒** |

入库是最窄的一段。消费组实测积压 380,641 条、`pending` 恰为 20,000（一个批大小），说明流水线确实在满负荷而非空转。

## 2. 排除的三个嫌疑

| 嫌疑 | 实测 | 结论 |
|---|---|---|
| InfluxDB 写入慢 | 单次写入 0.9 秒（WAL 刷盘间隔），但**每批只写一次**；CPU 0.16%、内存 592MB/2GB、数据目录 75MB | 排除 |
| JVM 内存上限（当日新加） | 堆占用 **12.6%**（144MB / 1.14GB）、GC 暂停 **0.008 秒/秒**、GC 0.37 次/秒 | 排除 |
| Redis `appendfsync always` | `XADD` 平均 6.92 µs，说明并非每条命令都刷盘 | 排除为主因 |

**排除 JVM 内存上限这一条尤其重要**：当日刚给 Java 服务加了容器内存上限，是最自然的怀疑对象；堆占用仅 12.6% 直接否定了它。

## 3. 定位

`PipelineProcessor` 处理一批的结构：

| 操作 | 频次 |
|---|---|
| InfluxDB 写入 | **每批一次** |
| `ack()` | **每批一次** |
| `markOnline()` → `PresenceStore.applyDataBatch` | **每批一次（pipeline）** |
| `TelemetryIngestor.prepare()` → `DeviceIdentityCache.find()` | **每条消息一次** |
| `ingestor.updateLatest()` → `LatestValueStore.update()` | **每条消息一次** |

前三项已经正确地批量化，后两项在逐条循环内。

- `DeviceIdentityCache.find()`：`redis.opsForValue().get(key)` —— 一次 GET
- `LatestValueStore.update()`：`redis.execute(UPDATE_LUA, ...)` —— 一次 EVALSHA

即 **每条消息 2 次网络往返**。

### 3.1 指标与代码互相印证

Redis `commandstats`（入库 952 条/秒时）：

| 命令 | 次/秒 | 每条消息 | 来源 |
|---|---|---|---|
| `hget` | 2,014 | 2.1 | **Lua 脚本内部**（`latest-update.lua` 有 2 次 `HGET`） |
| `hset` | 1,906 | 2.0 | **Lua 脚本内部**（同脚本 2 次 `HSET`） |
| `evalsha` | 990 | 1.0 | `LatestValueStore.update()` —— **网络往返** |
| `get` | 1,097 | 1.2 | `DeviceIdentityCache.find()` —— **网络往返** |

> **一个会把人带偏的坑**：Redis 的 `commandstats` **把 Lua 脚本内部调用的命令一并计数**。初次分析时把 `hget`/`hset` 也当成了独立往返，得出「每条 6 次往返」，据此预测约 1,100 条/秒，与实测峰值 2,943 不符。核对 `latest-update.lua` 后才发现这 4 次调用在服务端执行、无网络开销。

### 3.2 数量级吻合

2 次往返 × 约 0.15 毫秒 ≈ **0.3 毫秒/条 → 约 3,300 条/秒**，与实测峰值 **2,943 条/秒**吻合。

## 4. 改进方向（未实施）

把这两项按批量化，与 `markOnline` 现有写法一致：

1. **设备身份**：批内收集去重后的 `deviceKey`，一次 `MGET` 取回。600 台设备 / 20,000 条消息 → 由 20,000 次 GET 降为 1 次 MGET。
2. **最新值**：改为一次 pipeline 提交全批，或由 Lua 脚本一次处理多设备。

两项合计可把往返数由 `O(消息数)` 降为 `O(1)`/批。此后入库上限将由 InfluxDB 决定：批 20,000、单次写入 0.9 秒 → 理论约 22,000 条/秒，实际还会受解码与校验的 CPU 开销约束。

**注意**：`LatestValueStore.update()` 的 Lua 脚本按测点逐个比较时间戳以保证「旧数据不覆盖新值」。批量化必须保持该语义——这是遥测重放与乱序上报正确性的基础，不能为了吞吐放弃。

## 5. 未执行与限制

- **改进未实施**，上述 22,000 条/秒为按模型外推，未验证。
- 往返耗时 0.15 毫秒为按吻合度反推，未直接测量单次 Redis 往返的 RTT。
- 未分析 `prepare()` 中解码与物模型校验的 CPU 占比；若其耗时接近 0.3 毫秒/条，则批量化 Redis 后收益会被它限制。
- 本次数据取自一轮与其他操作并发的测量，中位数被压低（接入中位仅 397 条/秒），**仅峰值可用**；三段的稳态值需另做干净测量。
- `hmget` 19/s、`eval` 19/s 等低频命令未追溯来源。
