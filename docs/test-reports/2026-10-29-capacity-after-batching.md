# 容量测试：批量化之后的稳态入库能力

- 日期：2026-10-29（Asia/Shanghai）
- 被测版本：`cf9431c`（流水线入库路径批量化之后）
- 环境：压测机 192.168.126.129，Rocky Linux 10.2、8 核、7.5 GB 内存，standalone 栈 + 监控栈
- **测试类型：容量测试**（找积压不持续增长的最大稳态速率），非压力测试
- 负载端：开发机多进程发压（`tools/loadtest/`，28 进程）。**初版的 600 线程版本打不满，第 3 节三档数据因此不可用；第 7 节为升级负载端后的复测。**
- 结论：**可持续入库 ≥ 6,600 条/秒且队列零增长；入口天花板约 8,000 条/秒，由「单活 transport 一条连接消费全平台」的架构决定（EMQX 单连接 Erlang 信箱上限 1,000），调参无法突破。**

## 1. 关键数字（按项目约定记录 QPS 与 TPS）

| 指标 | 数值 | 测得条件 |
|---|---|---|
| **接入 QPS 峰值** | **8,431 条/秒** | 负载端多进程，目标 10,000；此速率下触发 19 次信箱溢出强杀 |
| **入库 TPS 峰值** | **6,839 条/秒** | 4,000 条/秒负载、队列为 0 的舒适区内 |
| 入库 TPS（接入 8,431 时） | 4,442 条/秒 | 伴随 19 次连接重建，低于舒适区峰值，差异未查清（见第 7 节） |
| **可持续容量** | **≥ 6,600 条/秒** | 3,000～6,000 四档积压均平稳、EMQX 队列全程为 0 |
| **入口天花板** | **约 8,000 条/秒** | 架构决定，见第 7 节 |
| 端到端延迟 | P50 1.5 秒 / P99 2.9 秒（4,000 条/秒时）<br>P99 5.6 秒（接入 8,431 时） | 见第 6、7 节 |
| 批量化之前的入库峰值 | 2,943 条/秒 | 对照基线 |

> **口径**：对外承诺能力只能用入库 TPS。过载时 EMQX 会先向设备 PUBACK 再丢弃，
> 接入 QPS 包含随后被丢掉的消息（2026-10-28 曾实测一轮丢弃 51,671 条）。
>
> **建议对外口径**：可持续 **6,000 条/秒**（留有余量的容量测试结论），
> 不要用 8,431（那是触发失效的速率）或 6,839（单点峰值）。

## 2. 低档位结果（3,000 ～ 6,000 条/秒）

四档各加压 180 秒：

| 目标 | 积压判定 | EMQX 队列 |
|---|---|---|
| 3,000 | 平稳 | 全程 0 |
| 4,000 | 平稳 | 全程 0 |
| 5,000 | 平稳 | 全程 0 |
| 6,000 | 平稳 | 全程 0 |

消费组 `lag` 在 52 ～ 4,232 之间波动但不单调上涨，每档结束后均排空。**6,000 条/秒仍在容量以内，未触及上限。**

## 3. 高档位结果：负载端先到极限

| 目标 | 实际接入中位 | 实际接入峰值 | 入库中位 | 判定 |
|---|---|---|---|---|
| 8,000 | 2,857 | 3,507 | 2,877 | **客户端未打满** |
| 10,000 | 1,679 | 2,015 | 1,667 | **客户端未打满** |
| 12,000 | 1,881 | 2,514 | 2,181 | **客户端未打满** |

**目标越高，实际打出的反而越少**（8,000 档 2,857，10,000 档 1,679）。这是客户端线程颠簸的典型特征：600 个 Python 线程各自 `sleep(min(0.02, ...))` 轮询，提高单设备速率后调度开销反噬；叠加 GIL，600 线程已接近该负载端的极限。

**因此这三档的数据不能用于判断系统容量**，只能得出「负载端打不到该速率」。

## 4. 方法：两次修正

### 4.1 速率不要自己做差分

初版脚本在 SSH 外侧每 20 秒读一次计数器、自己算差值。而 Prometheus 每 15 秒才抓一次，加上 SSH 往返耗时不固定，同一档位的单点值从 1,570 跳到 3,799，中位数被噪声压到约 2,400——据此一度误判「结论有问题」。

**改为由 Prometheus 的 `rate(...[1m])` 计算**，并丢弃每档前两个采样点（1 分钟窗口尚未填满）。改后数据平稳，与 `query_range` 的独立核对一致。

### 4.2 判「容量以内」之前必须确认喂进去的量达到了目标

初版只看积压涨不涨。但**若负载端根本没打满，队列当然不涨**——这不叫扛得住。该缺陷在低档位恰好没造成错误结论（实测确实喂进去了 6,626），但在高档位会直接把「客户端打不动」误判成「系统游刃有余」。

**修正**：接入 QPS 中位达到目标的 85% 才算打满，否则标注「结论不可用」。第 3 节三档正是靠这条判据被正确识别出来的。

## 5. 瓶颈的当前位置

批量化消除了「每条消息 2 次串行 Redis 往返」这道墙（详见 [2026-10-28 报告](2026-10-28-pipeline-redis-roundtrips.md)）之后：

- EMQX 队列在所有可测档位均为 **0** —— 出口不再是瓶颈
- 消费组 `lag` 只有瞬时波动，每档结束即排空
- **新的限制来自负载端，不是被测系统**

## 6. 端到端延迟（补测）

延迟指标 `conduit.pipeline.ingest.latency` 合并后补跑一轮，4,000 条/秒 × 180 秒：

| 时刻 | 接入 QPS | 入库 TPS | 延迟 P50 | 延迟 P99 | mqueue |
|---|---|---|---|---|---|
| 85s | 3,027 | 3,030 | 1,471 ms | 2,129 ms | 0 |
| 143s | 2,750 | 2,750 | 1,485 ms | 2,129 ms | 0 |
| 183s | 1,985 | 1,989 | 1,502 ms | 2,943 ms | 0 |

**延迟样本总数 707,207，与累计入库数 707,207 完全相等**，证明「每条成功入库记一次、死信不记」的设计落实正确。累计丢弃 0。

**入库 TPS 与接入 QPS 几乎完全重合**（3,030 vs 3,027），队列恒为 0：该速率下系统完全跟得上。

### 延迟的构成：WAL 刷盘是主导项

| 环节 | 量级 |
|---|---|
| transport 攒批（`batch-delay`） | ≤ 5 ms |
| Redis 总线 + 流水线取批 | 几十 ms |
| **InfluxDB 写入（等 WAL 刷盘）** | **约 900 ms**（单次写入实测 0.9 秒） |

**InfluxDB 的 `--wal-flush-interval`（默认 1 秒）占 P50 的约三分之二。** 这不是缺陷——写入返回即意味着已落盘，是用延迟换持久性。但它意味着：

> **本链路的延迟下限由 `--wal-flush-interval` 决定，而非由吞吐优化决定。** 无论如何批量化或扩容，只要该参数为 1 秒，P50 就不可能低于 1 秒。

需要更低延迟的场景，旋钮是该参数（代价是崩溃时可能丢失未刷盘数据），与 Redis `appendfsync` 属同一类取舍。**本次未改动该参数，也未做低刷盘间隔的对照测试。**

## 7. 负载端升级后：找到了架构天花板

第 3 节的三档因负载端打不满而结论不可用。将负载生成器由「每设备一线程」改为多进程
（`tools/loadtest/`，28 进程对应开发机 28 核）后复测，同样目标 10,000 条/秒：

| 同一目标 10,000 条/秒 | 旧版（600 线程） | 新版（28 进程） |
|---|---|---|
| 客户端 PUBACK 速率 | 1,679 条/秒 | **7,176 条/秒** |
| 提升 | — | **4.3 倍** |
| 客户端错误 | — | 0 |

负载端不再是瓶颈后，服务端的真实表现：

| 指标 | 峰值 |
|---|---|
| 接入 QPS | **8,431 条/秒** |
| 入库 TPS | **4,442 条/秒** |
| EMQX 队列 | **0**（全程） |
| 消费组 lag | 6,144（结束后排空至 5） |
| 延迟 P99 | **5,592 ms**（4,000 条/秒时为 2,129 ms） |

### 天花板的成因：单连接的 Erlang 信箱上限

本轮出现 **19 次 `check_oom_shutdown`，全部是 `mailbox_overflow`**，全部发生在 `conduit-transport` 这一条连接上：

```
shutdown: #{max => 1000, reason => mailbox_overflow, value => 9045}
policy:   #{max_mailbox_size => 1000}
```

信箱堆到 9,045 条（上限 1,000）。**此时 `max_inflight` 已是 512，远小于 1,000，所以不是在途消息撑爆的。**

成因是架构性的：**单活 transport 用一条 MQTT 连接消费全平台上行**，EMQX 需要把全部消息路由给**同一个 Erlang 进程**，而该进程的信箱上限为 1,000。路由速度超过处理速度即溢出——这与在途窗口无关，是**单连接的路由能力到顶**。

**结论：当前「单活 transport + 普通订阅」架构的入口天花板约 8,000 条/秒。** 要突破需要多实例 + 共享订阅，让路由压力分摊到多个连接进程上（该选项的阻塞前提已随 2026-10-28 关闭磁盘持久会话而消失，见 `CLAUDE.md` 第 4 节）。

### 失效后系统自愈，无数据丢失

| 检查项 | 结果 |
|---|---|
| EMQX 队列溢出丢弃 | **0** |
| EMQX 投递丢弃 `queue_full` | **0** |
| 消费组 lag | 已排空至 14 |
| 容器重启 | **0** |

19 次连接被杀之后，会话保留、transport 重连、未确认消息重投，系统自行恢复。

### 本轮的 QPS 与 TPS（按项目约定记录）

- **接入 QPS**：峰值 8,431 条/秒（含随后被堆积的部分）
- **入库 TPS**：峰值 4,442 条/秒
- **端到端延迟**：P99 5,592 ms（已明显劣化，说明该速率超出舒适区）

> 注意本轮入库峰值（4,442）低于第 6 节 4,000 条/秒那轮的 6,839。原因未查清——可能与 19 次连接重建导致的重投和重连开销有关。**该差异属未解释项。**

## 8. `max_mailbox_size` 对照实验：有用但不解决天花板

第 7 节定位到天花板来自单连接的 Erlang 信箱上限（默认 1,000）。该项是配置项，
因此先做一次廉价对照，看能否不动架构就把天花板上移。

同样目标 10,000 条/秒、600 台设备、120 秒：

| `max_mailbox_size` | 接入 QPS 峰值 | 入库 TPS 峰值 | 延迟 P99 峰值 | **失效事件** |
|---|---|---|---|---|
| 1,000（默认，基线） | 8,431 | 4,442 | 5,592 ms | **19 次** |
| **10,000** | 8,338 | **5,257** | 5,441 ms | **6 次** |

**结论：有用但不够。**

- 强杀由 19 次降到 6 次，入库峰值提升 18%——说明溢出**部分来自突发**，调大缓冲确有帮助。
- 但**调大 10 倍后仍有 6 次溢出**，说明也存在**持续超载**，不只是突发。
- **接入 QPS 几乎没变（8,431 → 8,338）**，即约 8,300 条/秒这道墙**不是信箱上限造成的**。

### 一处必须保留的不确定

**不能据此断定 8,300 就是系统的接入上限。** 同一负载端在第 7 节自身只打出 8,611 条/秒
（PUBACK 7,176），与 8,338 非常接近——**很可能又是负载端的墙**。要分清是系统还是客户端，
需要多机并发发压，单机测不出来。

### 方法记录：前三次实验均无效

本实验前后跑了四次，前三次的配置都没真正生效：

1. 远程 `sed` 的管道符未转义 → 表达式报错
2. `docker compose up -d` 未重建容器（需 `--force-recreate`）
3. 远程 Python heredoc 的换行转义被破坏 → 脚本语法错误

三次都是**静默失败**：外层命令退出码为 0，但配置没写成。第一次因此跑出了一组
「14 次失效、入库 5,782」的数据，差点被当成「调大有效」的证据。

**止损靠的是脚本里「回读生效配置，不符即中止」这一步。** 该做法已固化进
`docs/script/loadtest/` 的实践说明：**改远程配置必须回读确认，不能只看命令是否报错。**

根因是用「bash heredoc 包 Python、Python 再生成 Python」的套娃写法，每修一次又加一层转义；
正确做法是直接写文件再上传，全程不做字符串转义。

## 9. 未执行与限制

- **系统真实容量上限未知**，只知道 ≥ 6,600 条/秒。要测出天花板需要更强的负载端：Python 线程模型（600 线程 + GIL）已到极限，应改为多进程、或多台机器并发发压。
- 未测最大连接数：本次固定 600 条连接，瓶颈在速率而非连接数。
- 未做长时间浸泡：压测机磁盘仅 16 GB。
- 延迟只在 4,000 条/秒一个速率下取过数，**未测延迟随负载升高的变化**；也未做 `--wal-flush-interval` 的对照测试验证「WAL 占三分之二」这一归因。
- 低档位四档各仅一次测量，未做重复取样与显著性检验。
- 负载端与被测系统不在同一台机器，客户端侧的网络与调度开销未单独计量。
