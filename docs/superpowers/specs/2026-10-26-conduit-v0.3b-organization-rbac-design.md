# Conduit V0.3-B 设计：组织模型与 RBAC 2.0

- 日期：2026-10-26
- 状态：已批准；B1 已实现，B2～B4 待实施
- 分支：`codex/v0.3b-rbac-design`
- 前置：V0.3-A 租户隔离加固已合并到 `main`。
- 目标：把当前“一个租户只有管理员/只读两种全局角色”升级为可服务真实 SaaS 客户的组织、项目和数据范围权限体系，同时保持现有登录、租户隔离和设备接入链路可平滑迁移。

## 1. 当前问题

当前模型只有：

- 平台管理员 `PLATFORM_ADMIN`；
- 租户管理员 `TENANT_ADMIN`；
- 租户只读用户 `TENANT_VIEWER`。

JWT 直接携带一个有效角色，`SecurityConfig` 主要按路径和 HTTP 方法判断权限。这能表达“整个租户可写或只读”，但不能表达：

- 用户只管理某几个项目或站点；
- 同一用户在项目 A 是管理员、在项目 B 只读；
- 运维人员可以控制设备但不能管理用户或修改产品；
- 客户、项目、站点、资产之间的业务归属；
- 自定义角色、邀请、会话立即吊销和完整审计。

V0.3-B 不改变 tenant 作为数据隔离、资源配额和未来计费边界的定位。

## 2. 范围与拆分

V0.3-B 作为一个版本目标，但实施拆成四个可独立验收的阶段：

| 阶段 | 内容 | 可验收结果 |
|---|---|---|
| B1 组织骨架 | 客户、项目、站点、资产；设备归属；兼容现有数据 | 租户可建立层级并把设备分配到站点/资产 |
| B2 授权内核 | 权限目录、预置角色、作用域角色绑定、资源级鉴权 | 用户在不同项目拥有不同权限，越权统一为 404 |
| B3 身份治理 | 邀请、会话注册与吊销、密码策略、MFA 数据结构预留 | 邀请可追踪，禁用/改权后会话可立即失效 |
| B4 审计与界面 | 持久化审计、查询导出；组织与授权管理界面 | 敏感操作可按人、租户、项目、资源追溯 |

四个阶段使用同一份数据模型和权限词汇，避免先做临时角色再返工。

## 3. 组织模型

### 3.1 层级与职责

| 对象 | 所属 | 定位 | 是否安全边界 |
|---|---|---|---|
| 租户 `tenant` | 平台 | SaaS 客户账号、隔离、配额和计费边界 | 是，最高业务边界 |
| 客户 `customer` | 租户 | 租户服务的终端客户或内部业务单位 | 否，第一期只做业务归类 |
| 项目 `project` | 租户，可关联客户 | 权限分配和运营管理的主要范围 | 是，租户内授权边界 |
| 站点 `site` | 项目 | 工厂、园区、楼宇、电站等物理位置 | 是，可作为数据范围下钻 |
| 资产 `asset` | 站点，可有父资产 | 产线、配电房、机组、区域等业务对象 | 是，可作为数据范围下钻 |
| 产品 `product` | 租户 | 设备类型、编解码器和物模型模板 | 租户级共享，不属于项目 |
| 设备 `device` | 租户、产品；可分配站点/资产 | 实际接入实例 | 继承其项目/站点/资产范围 |

### 3.2 关系规则

- 一个客户可有多个项目；项目可不关联客户，支持租户内部项目。
- 一个项目可有多个站点；站点只能属于一个项目。
- 资产只能属于一个站点；资产允许树形嵌套，第一期最大深度建议限制为 8。
- 一个设备同一时刻只能归属一个站点，可选归属该站点下的一个资产。
- 设备的项目由站点推导，不重复让调用方传入冲突的 `project_id`。
- 产品继续在租户内共享。项目管理员可以使用已有产品创建设备，但修改产品及物模型需要租户级产品权限。
- 客户第一期不是登录主体，也不建立独立租户；需要客户门户时再基于项目成员关系开放。

### 3.3 兼容现有数据

- 新增一个系统项目和默认站点，承接每个现有租户的存量设备。
- 新表和新列先允许空值，后台迁移存量后再收紧约束，采用“扩展—迁移—收缩”。
- MQTT 鉴权、Transport、Redis 键和 InfluxDB 行协议不增加 project/site 标签；消息通过 PostgreSQL 设备身份取得组织归属，避免标签变更造成时序基数和历史迁移问题。
- 历史查询仍以 `tenant_id + product_key + device_key` 隔离；项目权限先在 PostgreSQL 验证设备归属，再查询 InfluxDB。

## 4. 权限模型

### 4.1 原则

- “角色”是权限集合，“绑定”决定角色在哪个范围生效。
- JWT 不承载完整权限列表或全部项目 id，只携带身份、租户、会话 id 和授权版本。
- 列表查询必须在 SQL 层加入授权范围，不能先读全租户数据再在 Java 中过滤。
- 单资源越权统一返回 404，不向调用者泄露资源存在性。
- 平台管理员代入租户时获得显式、可审计的临时租户管理员绑定语义，不伪装成真实租户用户。

### 4.2 权限词汇

权限使用稳定字符串，首期至少包含：

| 领域 | 权限 |
|---|---|
| 租户 | `tenant.read`、`tenant.manage` |
| 成员 | `member.read`、`member.manage`、`role.manage` |
| 客户 | `customer.read`、`customer.manage` |
| 项目 | `project.read`、`project.manage`、`project.member.manage` |
| 站点/资产 | `site.read`、`site.manage`、`asset.read`、`asset.manage` |
| 产品 | `product.read`、`product.manage` |
| 设备 | `device.read`、`device.manage`、`device.secret.rotate`、`device.command`（为 V0.4 预留） |
| 遥测 | `telemetry.latest.read`、`telemetry.history.read`、`telemetry.replay` |
| 审计 | `audit.read`、`audit.export` |

后端维护权限目录，数据库只引用目录中存在的权限码。删除或改名权限码必须走迁移，不允许运行时随意创建未知权限。

### 4.3 预置角色

| 角色 | 作用域 | 核心能力 |
|---|---|---|
| `TENANT_OWNER` | 租户 | 租户内全部权限；至少保留一个启用成员 |
| `TENANT_ADMIN` | 租户 | 日常管理全部资源与成员，不可转移所有权或删除租户 |
| `PROJECT_ADMIN` | 项目 | 管理项目、站点、资产、设备和项目成员 |
| `OPERATOR` | 项目/站点 | 查看并运维设备、查看遥测；不能管理成员和产品模板 |
| `VIEWER` | 租户/项目/站点 | 只读授权范围内资源 |

现有 `TENANT_ADMIN` 迁移为租户级 `TENANT_OWNER` 或 `TENANT_ADMIN` 需要明确规则；建议每租户最早创建的启用管理员成为 `TENANT_OWNER`，其余管理员成为 `TENANT_ADMIN`，现有 `TENANT_VIEWER` 成为租户级 `VIEWER`。

### 4.4 自定义角色

- 自定义角色属于一个租户，声明允许绑定的作用域类型：租户、项目或站点。
- 自定义角色只能组合当前操作者自己有权授予的权限，防止提权。
- 角色正在被绑定时不可删除；可停用，停用后绑定立即失效。
- 内置角色不可改权限、不可删除；名称可做本地化展示，稳定键不变。
- 第一版不支持条件表达式、字段级权限、按标签动态授权和“拒绝规则”；只有允许权限，避免 allow/deny 优先级失控。

### 4.5 继承与合并

- 租户级绑定覆盖租户内所有项目、站点和资产。
- 项目级绑定覆盖项目下所有站点、资产和设备。
- 站点级绑定覆盖该站点下所有资产和设备。
- 多个绑定取权限并集，不提供显式 deny。
- 客户不作为权限作用域；需要限制客户时，在其项目上批量绑定。
- 产品是租户级资源，只认租户级 `product.*` 权限；项目角色默认只有 `product.read`。

## 5. 数据模型（讨论稿）

### 5.1 组织表

- `customer(id, tenant_id, code, name, status, created_at, updated_at)`
- `project(id, tenant_id, customer_id nullable, code, name, status, created_at, updated_at)`
- `site(id, tenant_id, project_id, code, name, timezone, status, created_at, updated_at)`
- `asset(id, tenant_id, site_id, parent_id nullable, code, name, type, status, created_at, updated_at)`
- `device` 新增 `site_id`、`asset_id nullable`；迁移完成后 `site_id` 非空。

所有父子关系使用包含 `tenant_id` 的组合外键；站点到项目、资产到站点、设备到站点/资产都由数据库拒绝跨租户关联。资产关联设备时还必须保证资产属于设备站点。

### 5.2 授权表

- `role_definition(id, tenant_id nullable, role_key, name, scope_mask, built_in, status, created_at, updated_at)`
- `role_permission(role_id, permission_code)`
- `role_binding(id, tenant_id, user_id, role_id, scope_type, project_id nullable, site_id nullable, created_by, created_at)`

约束：

- `scope_type = TENANT` 时 project/site 均为空；
- `scope_type = PROJECT` 时只有 project 非空；
- `scope_type = SITE` 时 project 和 site 均非空，且 site 属于 project；
- 用户、角色和作用域对象必须属于相同租户；
- 相同用户、角色、作用域的绑定唯一。

为避免 `role_binding` 的多态外键失去数据库约束，实现时优先考虑拆成 `tenant_role_binding`、`project_role_binding`、`site_role_binding` 三张窄表；在实施计划前用实际查询复杂度和索引方案二选一。

### 5.3 会话、邀请、密码与 MFA

- `user_invitation`：租户、邮箱/用户名、邀请人、初始角色绑定草稿、一次性 token 哈希、过期时间、接受时间、撤销时间。
- `user_session`：会话 id、用户、租户、refresh token 哈希或 token family、创建/最后使用/过期/撤销时间、客户端摘要。
- `app_user` 新增 `authz_version`；角色或状态变化时递增，JWT 中的版本不一致即失效。
- 密码策略先支持租户级最小长度、复杂度、历史密码数量、最长有效期和登录失败锁定参数；平台提供安全下限，租户只能收紧。
- MFA 本期只预留 `mfa_method`/恢复码等数据结构与令牌声明，不在 B 阶段强制上线 TOTP 流程；真正启用前另写安全 spec。

不在日志、审计详情或数据库明文保存邀请 token、refresh token、密码、设备密钥和恢复码。

### 5.4 审计日志

`audit_event` 至少包含：

- `tenant_id`、`project_id`、`site_id`（适用时）；
- 操作者用户 id、用户名快照、有效身份；
- 代入者 id；
- 会话 id、请求 id、来源 IP、User-Agent 摘要；
- 动作、资源类型、资源 id、结果、失败码；
- 变更前后摘要（敏感字段脱敏）；
- 时间戳。

审计写入不得与主业务共享“失败就回滚并消失”的命运。第一版采用同库独立事务写入并监控失败；后续量大时可写 Outbox 再异步落审计存储。读取和导出本身也写审计。

## 6. 鉴权架构调整

### 6.1 JWT

保留：用户 id、租户 id、平台代入人、令牌类型。

新增：

- `sid`：会话 id；
- `av`：授权版本 `authz_version`。

移除对 JWT 单一 `role` 作为最终授权依据的依赖。过渡期可保留 role 声明供旧前端展示，但后端决策以数据库/缓存解析出的权限和数据范围为准。

### 6.2 后端授权

- `SecurityConfig` 只负责“是否登录、是否平台接口、是否进入租户”等粗粒度边界。
- 业务方法通过统一 `AuthorizationService` 检查权限码与作用域。
- 列表 Mapper 接收 `AuthorizedScope`，把项目/站点范围写入 SQL。
- 单资源服务先在带授权范围的查询中取资源；取不到统一 404。
- 禁止 Controller 自己拼权限逻辑；新增架构测试守住入口。

### 6.3 缓存与失效

- 权限解析结果可缓存在 Redis：`conduit:authz:{tenantId}:{userId}:{authzVersion}`。
- 修改角色、绑定、用户状态或组织归属时递增 `authz_version`，旧缓存自然失效。
- 会话撤销使用 `sid` 黑名单或会话状态查询；管理员执行“退出所有设备”后立即生效，而不是等待 15 分钟 access token 过期。
- Redis 不可用时鉴权回源 PostgreSQL；不能因为缓存失败而默认放行。

## 7. API 边界

建议新增：

- `/api/v1/customers/**`
- `/api/v1/projects/**`
- `/api/v1/projects/{projectCode}/members/**`
- `/api/v1/sites/**`
- `/api/v1/assets/**`
- `/api/v1/roles/**`
- `/api/v1/invitations/**`
- `/api/v1/sessions/**`
- `/api/v1/audit-events/**`

现有产品、设备、首页、历史和重放接口保持 URL 兼容，但查询结果按授权范围缩小。创建或移动设备时必须指定站点；过渡期未迁移客户端可落到默认站点，兼容窗口结束后取消该默认行为。

列表响应需要返回用户可见范围内的总数，不能暴露租户全量计数。批量接口逐项鉴权，并规定全成功或部分成功语义。

## 8. 安全规则

- 至少一个启用的 `TENANT_OWNER`；不能删除、禁用或撤销最后一个所有者的最终所有者绑定。
- 用户不能授予自己没有的权限，也不能操作高于自身管理范围的角色绑定。
- 组织节点移动必须重新验证设备、成员和子节点归属；跨项目移动写审计并使相关权限缓存失效。
- 停用项目/站点只阻止管理和未来控制命令，不默认阻断设备遥测接入；是否停止接入属于租户生命周期/设备生命周期策略，不能隐式耦合。
- 删除组织对象默认软删除或状态归档；有设备、资产、成员绑定时拒绝硬删除。
- 所有状态变更、授权变更、邀请、登录、刷新、登出、会话撤销、密码/MFA 变更、代入和敏感读取写审计。

## 9. 测试与验收判据

### 9.1 数据约束

- 所有组织父子关系跨租户写入被数据库拒绝。
- 设备不能关联其他站点的资产。
- 资产树不能成环，深度超过上限被拒绝。
- 最后一个租户所有者不能被撤销。

### 9.2 权限矩阵

- 租户管理员、项目管理员、运维、只读和自定义角色逐个覆盖组织、产品、设备、遥测、成员、角色、审计接口。
- 同一用户在项目 A 可写、项目 B 只读、项目 C 无权；列表、详情、计数、导出结果一致。
- 租户级权限正确继承到项目/站点；多个绑定取并集。
- 无权资源详情返回 404，不能通过错误信息、计数或导出推断存在性。

### 9.3 会话与审计

- 禁用用户、撤销会话、修改角色或绑定后，旧 access token 在下一次请求立即失效。
- Redis 不可用时回源数据库且不放宽权限。
- 邀请 token 只能使用一次，过期和撤销后无效。
- 每类敏感操作有审计记录，包含真实操作者和代入者；敏感值不入审计。

### 9.4 回归

- MQTT 鉴权、上报、最新值、在线状态、历史、重放和模拟器不因组织模型发生数据串租户。
- 现有租户管理员与只读用户迁移后权限不扩大也不意外丢失。
- `mvn -B verify`、前端测试与构建、可靠性 E2E 全部通过，并在 `docs/test-reports/` 留测试报告。

## 10. 发布与回滚

- 数据库按扩展—迁移—收缩至少分两个版本发布，不能在同一迁移中删除旧 role 语义。
- 第一阶段双读校验但仍由旧角色授权；对比新旧决策并记录差异。
- 第二阶段切换新授权内核，保留快速开关回退到只读保护模式；禁止在异常时默认放宽到租户管理员。
- 稳定一个版本后才移除旧 `app_user.role` 约束和 JWT role 决策代码。
- 部署前备份 PostgreSQL；回滚应用时新表保留，避免破坏已产生的组织与审计数据。

## 12. 已拍板

1. **租户与客户的关系**：租户是购买平台服务的合同/计费主体，客户只是租户内部服务对象，不允许客户跨租户。
2. **设备归属**：设备必须属于一个站点，可选属于站点内一个资产；不支持一台设备同时属于多个站点。
3. **产品归属**：产品保持租户级共享，项目只有使用权，没有独立复制产品。
4. **授权作用域**：第一期支持租户、项目、站点三级，不直接在单设备上绑定角色。
5. **自定义角色**：放在 B2 后半段；先用五个预置角色跑通权限内核。
6. **客户门户**：本期不做独立客户登录入口，用户仍是租户成员，通过项目角色限制范围。
7. **项目/站点停用**：不自动拒绝设备上报，只禁止管理操作和未来下行控制，避免运维误停用造成遥测缺口。
