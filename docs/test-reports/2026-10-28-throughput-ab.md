# 出口侧瓶颈定量对照与内存上限缺陷

- 日期：2026-10-28（Asia/Shanghai）
- 被测版本：`8dfefc5`
- 环境：压测机 192.168.126.129，Rocky Linux 10.2、8 核、7.5 GB 内存，standalone 栈 11 容器
- 负载：600 台设备 × 10 条/秒 = 6,000 条/秒（固定过载），每组 90 秒
- 方法：按 EMQX REST API 的 `send_msg` 相邻采样差值求速率，取中间若干次的中位数作为稳态值
- 结论：**吞吐的主导因素是 in-flight 窗口深度，不是批大小，也不是 Redis 刷盘策略**；同时发现部署包未给 Java 服务设内存上限，导致单个服务可占满宿主机内存

## 1. 对照结果

| 组 | `max_inflight` | `batch-size` | `appendfsync` | 稳态（条/秒） | 峰值 | 相对基线 |
|---|---|---|---|---|---|---|
| 基线 | 32 | 32 | always | **2,605** | — | — |
| A | 32 | 32 | **everysec** | 3,442 | — | +32% |
| B' | **256** | 32 | always | 3,842 | — | +48% |
| B1 | **256** | 32 | always | 3,662 | 4,432 | +41% |
| B2 | **256** | **256** | always | 3,309 | 4,014 | +27% |
| B3 | **1024** | **64** | always | **4,000** | 5,110 | **+54%** |

B' 与 B1 是同一配置的两次独立测量（3,842 / 3,662），复现良好。

## 2. 推翻的结论：「`batch-size` 必须等于 `max_inflight`」

该规则由 2026-10-28 早些时候写入计划、spec、`CLAUDE.md`、两个 `.env.example` 与 `SessionMonitor` 的判据，**本次实测否定**：

- 两组「相等」配置（32/32 = 2,605，256/256 = 3,309）都不是最优；
- 256/256 在三个变体中**垫底**；
- 最优的 1024/64 是 **16 倍**于批大小的窗口。

**原推理只有一半正确。** `batch-size > max_inflight` 时批确实永远攒不满、每批白等满 `batch-delay`，这半边成立；但由此推出「必须相等」是错的——`max_inflight` 大于 `batch-size` 恰恰是必要的：

- `inflight = batch`：EMQX 发 N 条 → 等 transport 全部确认 → 再发 N 条。**每批之间空一次完整往返，这是停等协议，流水线深度为 1。**
- `inflight >> batch`：transport 提交当前批时，下一批已在途中。流水线深度为 `inflight / batch`。

**正确规则：`batch-size ≤ max_inflight`，且 `max_inflight` 应为 `batch-size` 的若干倍。**

## 3. 强弱结论要分开看

**强信号（三轮独立测量一致，且有机理解释）**：把 `max_inflight` 提到 `batch-size` 之上能显著提升吞吐，+41% ～ +54%。

**弱信号**：B1（3,662）比 B2（3,309）高 10% —— 该差距可能落在测量噪声内。2026-10-28 的另一组数据显示同一配置两轮相差 33%（1,980 与 2,640）。因此本报告**不主张「8 倍优于 1 倍恰好 10%」**，只主张「没有任何数据支持必须相等，且相等的两组都不是最优」。

## 4. Redis 刷盘策略：有效但不建议采用

`appendfsync` 由 `always` 放宽到 `everysec` 带来 +32%，**低于单纯调整 in-flight 窗口的收益**，且代价具体：

> transport 是写入 Redis 成功之后才向设备回 PUBACK 的。改为 `everysec` 意味着 Redis 崩溃时**最多丢失 1 秒已经向设备确认过的消息**。

这正是本项目一整天在消除的那类「已确认但未收下」问题，因此该项**仅作瓶颈定位用途，不作为调优建议**。`appendfsync` 维持 `always`。

## 5. 部署缺陷：Java 服务没有内存上限

### 现象

压测后宿主机进入满 swap：

```
conduit-server   4.7 GiB / 7.468 GiB
可用内存         204 MB
Swap             2,037 MB / 2,048 MB（满）
```

重启 conduit-server 后立即恢复（server 464 MB、可用 4,529 MB），确认内存由其 JVM 堆持有。

### 根因

`deploy/standalone/docker/java.Dockerfile` 的入口是：

```
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]
```

`MaxRAMPercentage` 在容器**有**内存上限时按上限计算，**没有**上限时按宿主机总内存计算。实测四个 Java 容器各自自报最大堆 **5.60 GB**，而容器内存上限均为 0（无限制）：

| 容器 | 自报最大堆 | 容器内存上限 |
|---|---|---|
| conduit-server | 5.60 GB | **0** |
| conduit-transport ×2 | 5.60 GB | **0** |
| conduit-simulator | 5.60 GB | **0** |
| conduit-influxdb | — | 3 GB ✅ |

合计允许 22.4 GB，宿主机仅 7.6 GB。InfluxDB 的上限是此前为防止长范围查询拖垮宿主机单独加的，说明当时考虑过该风险，但只覆盖了一个服务。

**JVM 行为完全正确**——配置告诉它「取所见内存的 75%」，而无容器上限时它所见的是整台机器。

### 与流水线批大小的耦合

`conduit.pipeline.batch-size` 默认为 `-1`（不限），即一次取走 Redis 流中当前可读的全部消息；而流的 `MAXLEN` 为 100 万条。仅给容器加内存上限，可能把「宿主机 OOM」转化为「JVM OOM」。两项必须一起定。

## 6. 据此采取的措施

经所有者确认后实施（见同日提交与 `CLAUDE.md` 决定记录）：

1. 为各 Java 服务设置容器内存上限：server 1.5g、每个 transport 512m、simulator 384m，InfluxDB 由 3g 降至 2g。
2. `conduit.pipeline.batch-size` 由 `-1` 改为 **20000**。按「吞吐 ≈ 批大小 ÷ WAL 刷盘间隔 1 秒」计算，理论上限 2 万条/秒，远高于实测 4,000 条/秒的排空能力，既保住吞吐又封住内存。
3. `max_inflight` / `batch-size` 默认值由 32/32 改为 **1024/64**。
4. 更正「必须相等」的规则，并修正 `SessionMonitor` 的判据——原判据会把正确配置报成异常。

## 7. 未执行与限制

- **每组仅一次测量**，未做重复取样与显著性检验；绝对值应按区间理解。
- 未测 InfluxDB `--wal-flush-interval` 的对照（第三个候选成因），因此 4,000 条/秒的上限中 InfluxDB 占多大比重仍未知。
- 未在设置内存上限后复测吞吐，**上限是否会反过来限制吞吐未经验证**。
- 未验证 1024/64 在长时间运行下的内存与延迟表现，仅 90 秒窗口。
- 第一轮变体 B 因脚本用 `sed` 拼接字符串失败（`unterminated 's' command`），实际测成了 inflight 256 / batch 32 的配置；该次结果作为 B' 保留并复现，但当时未立即发现配置未按预期生效，**此类问题应由「每组回读生效配置」防住，第二轮已加入该步骤**。
