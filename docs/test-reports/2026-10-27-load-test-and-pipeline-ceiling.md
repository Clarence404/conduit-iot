# 压测报告：吞吐上限定位、根因与修复

- 日期：2026-10-27（Asia/Shanghai）
- 被测版本：`b71f389`（压测）→ `076ec17`（修复后复验）
- 环境：独占压测机，Rocky Linux 10.2、8 核 i7-14700、7.5 GB 内存、Docker 29.9.2，完整 standalone 栈 11 个容器
- 负载端：开发机 Python + paho-mqtt，每设备一条 MQTT 连接，QoS 1、不带消息 id
- 结论：**发现并修复了一个把平台吞吐钉死在 100 条/秒的缺陷**；另发现两个独立缺陷，其中一个为高危，尚未修复

## 1. 摘要

| 项 | 压测前 | 修复后 |
|---|---|---|
| 入库吞吐 | **约 100 条/秒** | **约 2780 条/秒**（提高 27.8 倍） |
| 瓶颈 | 流水线每批只写一次 InfluxDB，而写入要等 WAL 刷盘（1 秒） | 批大小默认不限，写入按字节切块 |
| 批大小配置 | 固定 100，无法调整 | `conduit.pipeline.batch-size`，`-1` = 不限（默认） |

同时发现两个本次**未修复**的缺陷，见第 5、6 节。

## 2. 方法与判据

客户端只能证明「平台已持久接收」（PUBACK），**不能证明已入库**。因此每轮都同时采服务端指标：Redis 消费组 `lag`（跟不上的第一信号）、`pending`、死信流长度、InfluxDB 实际行数、各容器 CPU/内存。

所有结论以服务端为准。正式加压前停掉演示模拟器，确认 10 秒内流增量为 0。

## 3. 压测发现：吞吐上限约 100 条/秒

第一轮按 1000 条/秒（200 设备 × 5/秒）打 180 秒：

**客户端全绿**：发送 180,873 条、全部确认、0 错误、PUBACK p50 1.0ms / p95 4.6ms / p99 51.8ms。

**服务端完全跟不上**：

| 时刻 | 消费组 lag |
|---|---|
| 24s | 11,044 |
| 88s | 68,574 |
| 152s | 121,197 |
| 195s | 162,572 |

停止加压后继续观察，`entries-read` 60 秒内增长 6,000，即 **100 条/秒**，且 `pending` 全程恒为 100（正好一个批次）。server 容器 CPU 仅 3～17%——**不是算不过来，是在等 I/O**。

**只看客户端会把这轮判成通过。** 健康检查、1Panel、EMQX 控制台在整个过程中都显示正常。

## 4. 根因定位（三步排除）

| 实验 | 结果 | 结论 |
|---|---|---|
| 批 100 / block 1s | 精确 100/秒 | 基线 |
| **批 1000** / block 1s | **998/秒** | 10 倍且完全线性 → 每批有固定开销 |
| 批 100 / **block 50ms** | 仍 100/秒 | **读取阻塞不是原因** |
| 直接测 InfluxDB 写 10 行 | **426 / 984 / 990 / 987 / 990 毫秒** | 就是它 |

`influxdb3 serve --wal-flush-interval` 默认 **1s**，而 `no_sync` 默认 false，写入要等下一次 WAL 刷盘才返回。流水线 `PipelineWorker` 是**单个虚拟线程**，每批只写一次 InfluxDB，于是：

> **吞吐 = 批大小 ÷ 1 秒**

批大小此前固定为 100，所以上限就是 100 条/秒。演示负载 17.4 条/秒只用到 17%，永远暴露不出来。

## 5. 新发现（高危，未修复）：EMQX 持久会话在负载下楔死

按 3000 条/秒打 150 秒后，EMQX 指标：

```
messages.received   929,524
messages.dropped          0        ← 没有丢数据
messages.persisted  902,187
messages.delivered  490,656        ← 约 41 万条停在这里
delivery.dropped          0
```

**投递完全停止**：80 秒内 `inflight=32`、`delivered_msgs`、`enqueued_msgs` 三个数字一动不动。此时所有可观测信号都是正常的——transport 健康 UP、`leader.connected=true`、EMQX `connected=true`、两侧日志零错误。

重启 transport **无法恢复**。EMQX 日志给出了机制：

```
[error] maximum heap size reached
Max Heap Size: 50331648   Total Heap Size: 57001396   (Erlang 字数，×8 字节)
emqx_ds_replication_layer:next/3
emqx_persistent_session_ds:replay_batch/4
```

**重放持久会话积压时连接进程超堆被杀**；transport 每次重连都重新触发重放、每次都被杀，形成死循环。`durable_sessions.batch_size` 已是 100，说明内存消耗来自 DS 层为取下一批而扫描存量条目，**积压越大重放越吃内存**。配置的 `force_shutdown.max_heap_size = "256MB"` 确认已生效，但实际触发值换算为 384 MB，说明重放进程不受该项约束。

恢复方式：停两个 transport → 以同 clientId、`cleanStart=true` 连接一次丢弃会话（`session_present=False`）→ 重启 transport。**代价是积压消息永久丢失**。

### 这推翻了 2026-10-27 早些时候的一条决定

`CLAUDE.md` 第 4 节记载「不实施会话异常检测」，依据是「第一次原因不明未复现、第二次是人为」。本次证明：

- **机制明确**：持久会话积压 → 重放超堆 → 进程被杀 → 死循环
- **可复现**：压测负载触发，无需人为 kick、无需停服务
- **触发条件普遍**：只要入库速度跟不上接入速度，积压就会堆起来——而修复前入库上限只有 100 条/秒
- **零可观测**：所有健康检查均为绿

该决定的前提已被证伪，需要重开。

## 6. 新发现（未修复 → 本次已修复）：批大小过大导致流水线永久停摆

把批大小设为 100,000 后：

```
InfluxDB HTTP 413: max request size (10485760 bytes) exceeded
```

`TelemetryWriter` 此前把除 400 外的所有 HTTP 错误都转成 `TelemetryUnavailableException`（可恢复），于是流水线**无限退避重试同一个超大载荷**（1s→30s 循环）。`entries-read` 冻结、`pending=99,400` 卡死，只有 WARN 日志、不进死信、健康检查仍为 UP。

> **批大小过小只是慢，过大是彻底停摆。**

## 7. 修复与验证（提交 `076ec17`）

1. **批大小可配置且默认不限**：`conduit.pipeline.batch-size`，`-1`（或任意非正数）= 不设 `COUNT`，取走当前可读的全部消息。
2. **写入按字节切块**：新增 `conduit.influx.max-request-bytes`（默认 8 MiB，低于 InfluxDB 默认的 10 MiB），`TelemetryWriter` 按累计字节切块发送，逐行拒绝的下标跨块正确映射回原始批内位置。**批再大也不会触发 413。**
3. **413 不再视为可恢复**：与 400 一并抛 `IllegalStateException`，作为切块失效时的兜底，避免再次出现无限重试停摆。

### 验证（压测机，批大小 `-1`）

| 检查项 | 结果 |
|---|---|
| 积压一次读取 | 211,491 条，`lag` 直接归零 |
| 413 出现次数 | **0** |
| 整批处理耗时 | 76 秒 |
| 实际入库行数 | **210,891，与发送数完全一致** |
| 死信 | 0 |
| 服务端告警/错误 | 无 |

**吞吐 210,891 ÷ 76 ≈ 2,780 条/秒**。

## 8. 接入侧（EMQX + transport）的观测

| 速率 | PUBACK p50 | p95 | 结论 |
|---|---|---|---|
| 500/秒 | 0.6 ms | 1.3 ms | 轻松 |
| 1000/秒 | 0.7 ms | 2.6 ms | 轻松 |
| 1500/秒 | 0.7～1.3 ms | 2.2～18.6 ms | 良好 |
| 3000/秒 | **486 ms** | **2951 ms**（max 6.9 秒） | 明显吃力，并触发第 5 节的楔死 |

接入侧可用上限在 **1500～3000 条/秒** 之间，超过后延迟急剧劣化。

- **第 5 节的楔死未修复**，仅定位到机制与恢复手段。

- **未测连接数上限**。本次最多 300 条并发连接，用提高单设备频率的方式逼近速率上限；真实的「最大设备数」需要另一套负载端（Windows + 线程模型撑不住上万连接）。

- **未跑 `conduit-e2e -Pe2e`**。
- 第 7 节的 2,780 条/秒是**排空积压**的速度，不是稳态入口速率——稳态还受第 8 节的接入侧上限约束。

### 11.1 修复过程中引入并修正的回归（如实记录）

把 `batch-size` 默认改成 `-1` 后，**第一次全量回归是 `BUILD FAILURE`**，`PipelineIT` 失败 2 项
（`unackedMessageIsClaimedAndProcessed`、`messageExceedingMaxDeliveriesGoesToDeadLetter`）。

原因是本次改动引入的回归：`XPENDING` 的 `COUNT` 必须为正数，没有「不限」的写法，而认领路径
（`claimStale`）也拿到了 `-1`。修正为：批大小非正时，单次认领退回有界值 1000——调用方本来就是
`while (claimOnce() > 0)` 反复取，分多次认领与一次取完等价。代码中已注释说明此处为何不跟随「不限」。

修正后 `PipelineIT` 20 项全通过，全量回归 699 项全通过。

排查中还踩到一个环境坑，记录备查：`mvn -pl conduit-server ...` **不会重建依赖模块**，会用本地仓库中
旧的 `conduit-common` jar，导致看到的仍是修改前代码路径的报错。须先 `mvn -pl conduit-common install`。
