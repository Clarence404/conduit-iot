# Conduit V0.2-R2 设计：端到端可靠上报

- 日期：2026-10-20
- 状态：已完成（2026-10-20，e2e 五个场景通过，含强杀 EMQX；见 `docs/test-reports/2026-10-20-demo-seed.md`）
- 范围：设备带消息 id 上报、平台在数据写入总线后回执、设备收到回执才删除本地副本；模拟器作为参考实现；e2e 验证强杀 EMQX 不丢数据。
- 前置：V0.2-R 已完成；EMQX 已统一为 5.10.5；Redis 已改为 `appendfsync always`（见 `docs/durability-validation.md`）。

## 1. 背景

`docs/durability-validation.md` 查明：EMQX 5.10.5 的 PUBACK 不代表消息已落盘。源码层面 `emqx_persistent_message:store_message/1` 使用 `#{sync => false}`，经 `gen_server:cast` 异步排队，默认 100 ms 刷新一次，RocksDB 写选项为空。实测强杀 Broker 进程，500 条中最多 142 条已 PUBACK 的消息丢失；客户机强制重启时三轮中两轮持久会话未恢复，500 条全部未取回。

这一跳是链路第一跳，无法绕开，也不是调参能解决的：调低刷新间隔不能消除异步排队与底层刷盘两个边界。平台内部其余各跳都遵守「下一跳收妥前不松手」，e2e 四个场景（杀 server、杀主 transport、杀全部 transport、重启 EMQX）均 500/500，链路本身不是丢数据的原因。

因此唯一可行的办法是把最终兜底交给设备：设备在收到平台回执前保留本地副本。此后平台内部任一环节（含 EMQX）崩溃都不会造成丢失，设备重发即可。

## 2. 目标

- 设备按本设计实现后，强杀 EMQX 进程不丢任何一条数据（e2e 断言计数恰好）。
- 不改变现有设备的行为：不带消息 id 的设备照常工作，不受影响。
- 不引入新的存储或进程。

不包含：去重存储、回执合并、下行指令通道、QoS 1 回执、界面展示设备是否使用可靠上报（见第 8 节）。

## 3. 协议契约

### 3.1 上行

沿用现有上行报文，把已有的 `id` 字段从「可选，仅用于追踪」改为「带上即启用可靠上报」。标准 JSON 与扁平 JSON 两种解码器下 `id` 都在顶层，语义相同（扁平 JSON 此前忽略 `id`，本期改为生效）。

```json
{ "id": "dev01-000123", "ts": 1760400000000, "params": { "Ua": 220.1 } }
```

| 字段 | 规则 |
|---|---|
| `id` | 字符串，1～128 个字符。同一设备内唯一即可，建议「设备标识 + 单调序号」。带上它即启用可靠上报 |
| `ts` | 带 `id` 时**必填**。这是重发不产生重复点的前提：同设备同 `ts` 覆盖为相同值，缺 `ts` 时平台用接收时间，重发会变成两个时间点 |

缺 `ts` 时平台照常回执并记一行 WARN，不拒绝、不进死信——拒绝会让设备无限重发。

### 3.2 回执

| 项 | 取值 |
|---|---|
| 主题 | `conduit/{productKey}/{deviceKey}/down/ack` |
| 内容 | `{"id": "<上行报文的 id>", "ts": <平台接收时间毫秒>}` |
| QoS | 0 |
| 粒度 | 一条上行一条回执，不合并 |

设备已有的订阅权限 `conduit/+/{deviceKey}/down/#` 覆盖该主题，ACL 无需改动。

QoS 0 的理由：回执丢失的后果只是设备重发，而重发是安全的；用 QoS 1 则设备离线时 EMQX 会在会话中堆积回执，而这些数据设备上线后本来就会重发。

### 3.3 语义

**回执表示「平台已持久接收」，不表示「数据已入库」。** 确认点是写入 Redis 总线成功，物模型校验在其后的流水线中进行。校验不合格的测点仍会被剔除并记 `FIELD_REJECTED` 死信，重发不会改变结果。设备收到回执即应删除本地副本。

选择这个确认点的原因：Redis 已配置 `appendfsync always`，写入返回即已刷盘；而等到写完 InfluxDB 再回执会延长链路、增加回传复杂度，且 InfluxDB 之后的重试由流水线保证。

## 4. transport 改动

`MqttProtocolAdapter.onPublish` 现有顺序是「写总线成功 → 回 PUBACK」，在其后增加一步「发回执」：

1. 从 payload 浅解析顶层 `id` 与 `ts` 是否存在，只读这两个字段，不解析 `params`，不依赖产品解码器；
2. 没有 `id`、payload 不是 JSON 对象、或解析失败：跳过回执，记 DEBUG，行为与现在完全一致；
3. 有 `id` 但缺 `ts`：照常回执，并记一行 WARN 指出重发可能产生重复点（按设备限流，同一设备最多每分钟一行，避免刷屏）；
4. 有 `id`：向 `conduit/{productKey}/{deviceKey}/down/ack` 发 QoS 0 回执，`ts` 取该消息的 `receivedAt`；
5. 回执发送失败只记 WARN，不重试，不影响已回的 PUBACK——丢了设备会重发。

回执使用当前会话的 MQTT 连接，不新建连接；仅主实例发送（只有主实例连接 EMQX）。浅解析按 UTF-8 读取，payload 超过 64 KB 时跳过解析（正常上行远小于此）。

只有上行数据消息（`MessageType.PROPERTY`）走这条路径；`$SYS` 上下线事件不回执。

## 5. 模拟器：参考实现

模拟器改为带 `id` 上报，并实现设备侧待确认队列，同时作为设备开发者的参考实现：

- 每台设备维护单调序号，`id` 形如 `{deviceKey}-{序号}`，`ts` 必填；
- 发送后进入待确认队列，收到回执按 `id` 出队；
- 超时未收到回执则重发，超时时间可配（`SIM_ACK_TIMEOUT_MS`，默认 30000）；
- 队列上限可配（`SIM_MAX_PENDING`，默认 1000），超过上限时暂停产生新数据而不是丢弃；
- 模拟器订阅自己的 `down/ack` 主题。

**限制（文档写明）**：模拟器的待确认队列只在内存中，用于验证平台侧；真实设备必须把队列持久化到本地存储，否则设备自身断电仍会丢数据。

## 6. 测试

### 6.1 e2e 新增场景

在 `ReliabilityE2EIT` 增加第 5 个场景「强杀 EMQX 进程」：

- 设备由测试代码扮演，实现与第 5 节相同的待确认队列（收到回执才出队，超时重发）；
- 10 台设备各 50 条，共 500 条，发送中途 `docker kill -s KILL` EMQX 容器并重启；
- 断言：InfluxDB 中该产品恰好 500 条，无死信，消费组无未确认消息。

这是当前会丢数据的场景，是本设计成立与否的判据。原有四个场景保持不变。

### 6.2 transport 集成测试

- 带 `id` 的上行收到回执，内容与 `id` 一致；
- 不带 `id` 的上行不产生回执；
- payload 不是 JSON 时不回执且数据照常入库；
- 回执发送失败（模拟连接异常）不影响数据入库与 PUBACK。

### 6.3 模拟器单元测试

- 收到回执才出队；
- 超时重发，重发使用相同的 `id` 与 `ts`；
- 回执乱序到达时按 `id` 正确出队；
- 队列达到上限时暂停产生新数据。

## 10. 链路精简评估（2026-10-20，结论：暂不精简）

立项时约定：可靠上报做完后评估能否精简链路，因为设备成为最终兜底之后，平台内部各环节的持久性不再是「不丢」的依靠。评估结论是两条路都卡在前置条件上，本期不动代码。

### 10.1 关闭 EMQX 磁盘持久会话——不可行

前提是所有设备都走可靠模式。但第 3 节选定的启用方式是「报文带 `id` 即启用」，契约上明确允许设备不带 `id`，这些设备仍然依赖平台兜底。关掉持久会话会让它们在 transport 离线或 EMQX 重启时丢数据，属于对既有契约的回退。

要解除这个前提，得先把可靠模式定为唯一支持的模式，那是协议层的收紧，应单独立项讨论。

### 10.2 删除 transport 选主机制——受 EMQX 版本阻塞

删掉选主的前提是用共享订阅分摊多实例，而 EMQX 5.10.5 的磁盘持久会话拒绝共享订阅（SUBACK `SHARED_SUBSCRIPTIONS_NOT_SUPPORTED`，0x9E）。实测 6.3.0 两者可以同时使用（订阅被批准，离线积压 2000 条全部补回，带未确认消息恢复也正确），但升级到 6.x 有两个未决问题：

- 镜像自报 EMQX Enterprise 并带社区许可，到期日 2029-03-01，许可条款与到期行为未评估；
- 6.3.0 在存在未确认消息时完全停止推进投递（实测 S1 只收到 1～101 便停住），在途窗口被压到 1 条，吞吐影响未测。

这两点属于「升级 EMQX」的范畴，backlog 中已有该条目。

### 10.3 Redis 总线的定位——维持现状

总线从「可靠性必需品」降级为「削峰与重试的便利设施」这一判断成立，但它同时承担消费组、`XPENDING` 认领与死信，这些能力与可靠上报无关，不因设备兜底而失去价值。没有删除或替换的理由。

### 10.4 重新评估的触发条件

出现以下任一情况时重新评估：可靠模式定为唯一支持的模式；或 EMQX 升级到同时支持持久会话与共享订阅、且许可与吞吐两项疑问均已澄清的版本。
