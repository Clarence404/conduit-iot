# V0.4-A1 单设备指令设计（2026-11-25）

V0.4-A 设备控制最小闭环的第一步。后两步各自另写 spec：A2 期望属性 / 设备影子（离线下发），A3 批量任务。

## 1. 目的

平台目前只有上行：设备能上报，平台不能给设备发任何东西。本步让运维人员在设备详情页对**一台在线设备**调用物模型中定义的「服务」，几秒内看到设备的执行结果，并留下指令记录。

本步同时打通「server → transport → 设备」的下行链路和「设备 → 平台」的回执链路，A2、A3 都建在它上面。

典型场景（演示数据要覆盖）：
- 智能水表开阀 / 关阀；关阀后上报的瞬时流量变为 0。
- 光伏逆变器设有功限值（百分比）；之后上报的功率不超过额定功率 × 限值。
- 设备执行失败（返回非 0 结果码）、设备不响应（超时）、设备离线（不发送）。

## 2. 目标、不做的事、失败标准

**目标**
1. 物模型增加「服务」定义：标识、名称、输入参数（类型与约束沿用属性的类型体系）、超时。
2. 下发指令：参数按服务定义校验，设备在线才下发，记录完整状态，设备回执后更新结果。
3. 状态区分「确定没执行」与「结果未知」：发不出去、过期未发、设备未订阅为确定未执行；已发出但没收到回执为结果未知。
4. 设备详情页「控制」标签：发送指令、看结果、看本设备的指令记录。
5. 模拟器按服务响应，演示设备行为随指令变化。
6. 下行链路经 transport，为以后的 HTTP / 私有 TCP 适配器复用。

**不做**（以后的步骤或另行评估）
- 离线排队、期望属性、设备影子：A2。
- 批量下发、按组 / 站点选设备、灰度、失败阈值中止：A3。
- 取消指令。有效期最长 60 秒，取消的意义不大，A3 的批量任务再做。
- 定时指令、指令模板、OTA、凭据轮换。
- 服务的输出参数定义。回执里的 `data` 原样保存、原样展示，不校验。
- 设备主动调用平台（设备 → 平台的 RPC）。
- HTTP、私有 TCP 适配器本身。

**失败标准**（即使功能能用，出现以下情况也算没做好）
- 设备超时没回执，却显示「失败」或「未执行」。超时只能显示「结果未知」。
- 指令在设备离线时被静默丢弃，用户看不到原因。
- 一条指令被设备执行两次，而协议没有给设备去重的依据。
- 下发阻塞上行：下行流积压或 transport 发不出去，导致上行变慢或丢数。
- 越权：用户能对自己无权访问的设备下发，或看到其他租户的指令记录。

## 3. 方案对比（所有者 2026-11-25 选 B）

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | server 调 EMQX 发布接口 `/api/v5/publish` | 最快，不加组件；但下发只认 EMQX，以后的 TCP / HTTP 设备连在 transport 上，届时要另开一条下发路径 |
| **B（选定）** | server 写下行流 `conduit:stream:down`，transport 消费后用自己的 MQTT 连接发布 | 上下行都经协议层 transport，以后加适配器直接复用；多一条 Redis 流和 transport 里一个消费者 |
| C | server 自带 MQTT 客户端 | 把 transport 的连接、鉴权、重连在 server 再做一遍，同样只认 MQTT，不取 |

回执的路三种方案相同：设备发 `up/reply`，沿上行链路回到 server。

## 4. 设备协议

### 4.1 下发

- Topic：`conduit/{productKey}/{deviceKey}/down/service`，QoS 1。设备 ACL 已允许订阅自己的 `down/#`，不用改。
- Payload：

```json
{ "id": "c-01JD3K…", "service": "setValve", "params": { "open": false }, "ts": 1764000000000, "expiresAt": 1764000010000 }
```

- `id`：指令 id，全局唯一，1～64 字符。**同一 `id` 可能收到不止一次**（见 6.4），设备须按 `id` 去重：已执行过的 `id` 不再执行，直接重发上次的回执。
- `ts`：平台发出时间；`expiresAt`：过期时间（毫秒）。设备收到时已过 `expiresAt` 的指令不执行，回执 `code = -1`（见 4.2）。

### 4.2 回执

- Topic：`conduit/{productKey}/{deviceKey}/up/reply`，QoS 1。
- Payload：

```json
{ "id": "c-01JD3K…", "code": 0, "message": "ok", "data": { "valve": "closed" } }
```

- `code`：整数，0 为成功，非 0 为失败；约定 `-1` 表示设备因过期未执行。`message` 可选，最长 256 字符；`data` 可选，任意 JSON 对象，序列化后不超过 4 KiB。
- 不合法的回执（不是 JSON、缺 `id`、`code` 不是整数、超长）进死信 `INVALID_REPLY`，不影响指令状态。

### 4.3 接入指南

`docs/device-integration.md` 新增一节：订阅下发 topic、按 `id` 去重、过期不执行、回执格式，并附 Python 示例。

## 5. 数据模型（Flyway V11）

### 5.1 服务定义 `product_service`

| 列 | 说明 |
|---|---|
| `id`、`tenant_id`、`product_id` | 组合外键 `(tenant_id, product_id)` 指向 `product`，与 `product_property` 一致；产品删除时级联删除 |
| `identifier` | `^[A-Za-z][A-Za-z0-9_]{0,63}$`，同一产品内唯一 |
| `name`、`description` | 名称必填，最长 64；描述可选，最长 256 |
| `input_params` | jsonb 数组，每项 `{identifier, name, dataType, required, min, max, decimals, enumItems, unit}`；`dataType` 为 DOUBLE / INT / BOOL / TEXT / ENUM，约束规则与属性相同；最多 16 个参数 |
| `timeout_seconds` | 5～60，默认 10 |
| `created_at`、`updated_at` | |

- 接口：`GET/POST /api/v1/products/{productKey}/services`、`PUT/DELETE /api/v1/products/{productKey}/services/{identifier}`；读需要 `product.read`，写需要 `product.manage`。
- 界面：产品详情页物模型区分「属性」「服务」两个标签，服务可增删改，参数编辑复用属性的类型与约束控件。
- 服务定义修改或删除后，已有指令记录不受影响（记录保存下发时的服务标识与参数快照）。

### 5.2 指令记录 `device_command`

| 列 | 说明 |
|---|---|
| `id` | 文本主键，格式 `c-` + ULID，同时作为协议中的 `id` |
| `tenant_id`、`device_id` | 组合外键指向 `device`；设备删除时级联删除 |
| `device_key`、`product_key` | 冗余保存，供 transport 与回执匹配 |
| `service`、`params` | 服务标识与参数快照（jsonb） |
| `status` | 见 5.3 |
| `created_by`、`created_by_name`、`impersonated` | 发起用户 id（不设外键：平台管理员代入租户时，会话里的用户就是平台管理员本人，没有 `tenant_id`）、用户名快照、是否代入租户发起 |
| `created_at`、`sent_at`、`finished_at`、`expires_at` | |
| `reply_code`、`reply_message`、`reply_data`、`late_reply` | 设备回执；超时后才到的回执 `late_reply = true` |
| `failure_reason` | NOT_SENT 的确定原因：`NO_SUBSCRIBER`、`EXPIRED_BEFORE_SEND`；TIMED_OUT 时可附 `NO_DISPATCH_REPORT`（到期仍未收到 transport 的发送报告）或 `TAKEOVER_UNKNOWN`（接手的实例无法确认前一个实例是否已发出） |

- 索引：`(tenant_id, device_id, created_at desc)` 供列表；`(status, expires_at)` 供超时清扫。
- 保留：记录保留 90 天，每天清理一次（与超时清扫同一个守护线程）。

### 5.3 状态

**原则：只有拿到确定证据才判「没执行」（NOT_SENT），其余不确定的一律是「结果未知」（TIMED_OUT）；之后到达的更确定的证据可以改写较早的状态。**

```
PENDING ──transport 报告已发出──────────▶ SENT ──回执 code=0──▶ SUCCEEDED
   │                                        │ ──回执 code≠0──▶ FAILED
   │                                        └─到期无回执────▶ TIMED_OUT（结果未知）
   ├─transport 报告「发送前已过期」────────▶ NOT_SENT（EXPIRED_BEFORE_SEND）
   ├─transport 报告 EMQX「无订阅者」───────▶ NOT_SENT（NO_SUBSCRIBER）
   └─到期 + 宽限期仍无任何报告─────────────▶ TIMED_OUT（结果未知，NO_DISPATCH_REPORT）
```

- 终态：SUCCEEDED、FAILED、NOT_SENT；TIMED_OUT 是「暂定终态」，允许被之后的证据改写。
- 改写规则（server 流水线按指令 id 处理，全部幂等）：
  - 设备回执（任何时候到达）：PENDING / SENT / TIMED_OUT / NOT_SENT → SUCCEEDED 或 FAILED。超时或已判 NOT_SENT 之后才到的回执标 `late_reply = true`；NOT_SENT 被回执改写时记一行 WARN（说明平台的判断被设备推翻，用于排查）。
  - transport 的 SENT 报告：PENDING / TIMED_OUT → SENT；若 SENT 报告到达时已过期，直接记为 TIMED_OUT 并填 `sent_at`。
  - transport 的 NOT_SENT 报告：只把 PENDING / TIMED_OUT 改为 NOT_SENT；SENT 及之后的状态不受影响。
  - 同一状态的重复报告与重复回执不改变任何字段。
- **NOT_SENT 是「确定没执行」**，**TIMED_OUT 是「结果未知」**，界面必须用不同颜色和文字区分。
- 设备回执 `code = -1`（过期未执行）记为 FAILED，`reply_code = -1`，界面显示「设备判定已过期，未执行」。

## 6. 下行链路

```
浏览器 ─POST─▶ server ─INSERT device_command(PENDING)─▶ PostgreSQL
                   └─XADD conduit:stream:down────────▶ Redis
transport（消费组 conduit-transport-down）─PUBLISH QoS1─▶ EMQX ─▶ 设备
transport ─XADD conduit:stream:up（COMMAND_DISPATCH：SENT / NOT_SENT / UNKNOWN 及原因）─▶ server 流水线 ─UPDATE─▶ PostgreSQL
设备 ─up/reply─▶ EMQX ─▶ transport ─XADD conduit:stream:up（COMMAND_REPLY）─▶ server 流水线 ─UPDATE─▶ PostgreSQL
```

### 6.1 server 下发

1. 校验：用户对该设备有 `device.command`（沿用设备范围授权）；服务存在；参数逐个按定义校验（类型、必填、上下限、小数位、枚举），不合格返回 400 并指出参数。
2. 设备必须启用、在线（`conduit:presence` 的 `online = true`），否则 409 `DEVICE_OFFLINE` / `DEVICE_DISABLED`，不建记录。
3. 同一设备未结束（PENDING / SENT）的指令最多 5 条，超过返回 409 `TOO_MANY_PENDING`。
4. 事务内插入 PENDING 记录；**事务提交后**写下行流。写流抛出异常时无法确定是否已写入（例如客户端超时但 Redis 已执行），记录保持 PENDING，由超时清扫转为 TIMED_OUT；接口返回 503 `COMMAND_DISPATCH_UNCERTAIN`，提示「下发结果未知，请查看指令记录」。
5. 返回 202 和指令记录。
6. 管理操作日志：每条下发记一行 INFO（指令 id、设备、服务、操作人），不记参数值。

### 6.2 下行流 `conduit:stream:down`

- 条目字段：`commandId`、`productKey`、`deviceKey`、`topic`（如 `down/service`）、`payload`（4.1 的 JSON）、`expiresAt`。
- 长度上限 `MAXLEN ~ 100000`。经 `MessageBus` 新增的下行接口读写，Redis Streams 实现；以后换 MQ 时一并替换。
- 消费组 `conduit-transport-down`，每个 transport 实例一个消费者（名为 instanceId）。

### 6.3 transport 消费与发布

- 本实例至少持有一个已连接的身份时才读下行流；没有就不读，避免拿到发不出去的指令。
- 逐条处理：
  - 已过 `expiresAt`：不发，写 `COMMAND_DISPATCH(NOT_SENT, EXPIRED_BEFORE_SEND)`。
  - 否则选本实例一个已连接的身份（轮流），QoS 1 发布到 `conduit/{productKey}/{deviceKey}/{topic}`，并设 MQTT 5 消息过期间隔 = 距 `expiresAt` 的剩余秒数（向上取整，至少 1 秒）。这样设备刚离线、但会话仍在 EMQX 时，指令在会话队列中到期即被丢弃，不会在设备几小时后上线时才送达：
    - EMQX 回 PUBACK 成功：写 `COMMAND_DISPATCH(SENT, sentAt)`。
    - PUBACK 原因码为「无匹配订阅者」：写 `COMMAND_DISPATCH(NOT_SENT, NO_SUBSCRIBER)`。
    - 发布异常（连接断开等）：不 ack，留给重试。
  - `COMMAND_DISPATCH` 写入上行流成功后，才 ack 下行流条目。
- 认领：实例宕机后，其未 ack 的条目空闲超过 10 秒由其他实例 `XCLAIM` 接手。接手的实例无法知道前一个实例是否已发出：未过期就照常再发一次（设备按 `id` 去重）；已过期则**不报 NOT_SENT**，而是写 `COMMAND_DISPATCH(UNKNOWN, TAKEOVER_UNKNOWN)`，server 据此把 PENDING 记为 TIMED_OUT。
- **下发不得拖慢上行**：下行消费用独立线程，与 `SharedBatcher` 互不阻塞；一个设备的发布失败不阻塞其他条目。下行发布占用的 inflight 计入该连接的窗口，下行量远小于上行，不单独限流（A3 批量时再评估）。

### 6.4 至少一次与去重

- 发布与 ack 之间崩溃会导致同一指令被发两次，这是有意的取舍：宁可重发，也不让已提交的指令丢失。
- 设备按 `id` 去重（4.1）；server 对重复的 `COMMAND_DISPATCH` 与回执都幂等（只在允许的源状态下更新）。

### 6.5 回执与状态更新（server 流水线）

- `MessageType` 新增 `COMMAND_REPLY`（来自设备 `up/reply`）与 `COMMAND_DISPATCH`（来自 transport）；transport 的 `TopicParser` 识别 `reply`。
- 流水线按指令 id 更新，条件必须同时匹配 `device_key` 与身份缓存给出的 `tenant_id`，防止设备伪造他人指令 id。匹配不到的回执进死信 `UNKNOWN_COMMAND`。
- 更新失败（数据库不可用）按现有可恢复错误规则退避重试，不消耗投递次数。

### 6.6 超时清扫

- server 守护线程每 2 秒执行一次，只产生「结果未知」，从不产生 NOT_SENT：
  - SENT 且 `expires_at < now()` → TIMED_OUT。
  - PENDING 且 `expires_at + 宽限期 < now()` → TIMED_OUT（`NO_DISPATCH_REPORT`）。宽限期默认 30 秒，可配置：transport 的发送报告与遥测走同一条上行流，积压时会晚到，宽限期让它们有机会先到。
- 单条 `UPDATE … WHERE` 条件语句，多个 server 实例并行执行也安全。

## 7. 接口与界面

### 7.1 接口

- `POST /api/v1/devices/{deviceKey}/commands`，body `{service, params}` → 202 + 指令记录。需要 `device.command`。
- `GET /api/v1/devices/{deviceKey}/commands?page&size&status` → 分页列表，按时间倒序。需要 `device.read`。
- `GET /api/v1/devices/{deviceKey}/commands/{id}` → 单条。需要 `device.read`。
- 授权沿用设备的项目 / 站点范围：先经受租户与范围过滤的查询拿到设备，再按 `device_id` 查指令。
- `PermissionGateFilter` 把 `POST /devices/{deviceKey}/commands` 映射到 `device.command`（现在会落到 `device.manage`）。
- 授权模式与其他写操作一致：`enforce` 下按 `device.command` 与项目 / 站点范围执行；默认的 `shadow` 下只记录判定结果，实际按旧路径矩阵放行，即租户管理员可对本租户全部设备下发、只读用户不能下发。不为指令单独强制 `enforce`。测试两种模式都覆盖。

### 7.2 设备详情「控制」标签

- query `tab=control`，在 `ROUTE_META` 登记。
- 有 `device.command` 才显示发送区；只读身份只看记录（隐藏发送区，不禁用）。
- 发送区：选服务 → 按参数定义生成表单（BOOL 单选、ENUM 下拉、数值带上下限与单位、TEXT 输入框）→ 发送。设备离线时发送按钮旁提示「设备离线，无法下发」。
- 发送后在列表顶部插入该条，每秒轮询它的状态直到终态（最长有效期 + 5 秒）。
- 指令记录用 `useTable`，列：时间、服务（名称 + 标识）、参数、状态（SUCCEEDED 绿、FAILED 红、TIMED_OUT 橙「结果未知」、NOT_SENT 灰并显示原因、PENDING / SENT 蓝）、耗时、回执、操作人（代入时注明）。
- 产品未定义服务时显示空状态，并给出跳转到产品物模型「服务」标签的按钮。

## 8. 模拟器

- 订阅 `conduit/{productKey}/{deviceKey}/down/service`。
- 按 `id` 去重：缓存最近 1000 个已处理的 `id` 及其回执，重复收到直接重发回执。
- 处理延迟随机 200～800 毫秒，模拟真实设备。
- 演示行为（按产品与服务标识识别，其他服务一律回执成功）：
  - 智能水表 `setValve(open)`：关阀后流量测点上报 0，开阀后恢复正常曲线。
  - 光伏逆变器 `setPowerLimit(percent)`：之后功率按 `额定 × percent / 100` 截顶。
  - `selfTest`：在线时回执失败 `code = 2`，`message` 为「自检未通过（演示）」，用于演示失败。
  - `diagnose`：不回执，用于演示超时（结果未知）。
- 过期指令不执行，回执 `code = -1`。

  - server：下发接口的授权（无 `device.command`、范围外设备、跨租户）、离线 409、待处理上限、事务后写流、写流失败转 NOT_SENT；流水线处理 `COMMAND_DISPATCH` / `COMMAND_REPLY`，伪造 id 进死信；超时清扫。
  - transport：真实 EMQX 下，设备订阅后收到下发、未订阅得到 NO_SUBSCRIBER、过期不发、无已连接身份时不消费、宕机条目被认领。
- e2e：新增场景「指令往返」：3 个 transport，向一台在线的带回执设备下发 20 条指令（使用超时 60 秒的服务，留出 10 秒认领与重发的时间），期间强杀一个 transport；断言每条指令最终是 SUCCEEDED、设备对每个 id 只执行一次，上行计数仍守恒。另测：发送报告晚到时清扫只产生 TIMED_OUT，之后的回执能把它改写为 SUCCEEDED。
- 前端：控制标签按权限显示、表单按参数类型生成、轮询到终态停止、状态颜色与文字。

## 13. 设计中由 Claude 决定、待所有者核对的点

所有者确定的：分三步（A1 单设备指令 → A2 期望属性 / 影子 → A3 批量任务）、A1 只对在线设备下发且不排队、物模型增加服务、设备详情「控制」标签、模拟器响应指令、下行走方案 B。以下是写设计时的取舍：

1. 只有确定证据才判 NOT_SENT，其余一律 TIMED_OUT（结果未知），之后的证据可改写；清扫给发送报告 30 秒宽限期。
2. 下发带 MQTT 5 消息过期间隔，设备刚离线时指令在 EMQX 会话里到期即丢弃。
3. 指令授权跟随全局授权模式（`shadow` 下按旧路径矩阵），不单独强制。
4. 不做取消；单设备未结束的指令最多 5 条；记录保留 90 天；服务超时 5～60 秒，默认 10 秒；参数最多 16 个；回执 `data` 不超过 4 KiB。
5. 指令 id 为 `c-` + ULID；`created_by` 不设外键，另存用户名快照与是否代入。
6. 界面每秒轮询单条指令直到终态，不用推送。
7. 演示：水表 `setValve` / `selfTest`，逆变器 `setPowerLimit` / `diagnose`，两个电表产品 `selfTest`；`selfTest` 演示失败、`diagnose` 演示超时。
