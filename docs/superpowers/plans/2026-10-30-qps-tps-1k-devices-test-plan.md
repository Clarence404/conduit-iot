# 测试计划：1,000 台设备逐档提速，测接入 QPS 与入库 TPS

- 日期：2026-10-30（计划，**未执行**）
- 测试类型：容量测试（找积压不增长、无掉线、时延达标的最大稳态速率），按 `CLAUDE.md` 2.2 的约定同时记录接入 QPS 与入库 TPS
- 前序：同日「N 台设备 × 每台每秒 1 条」阶梯已按所有者要求**暂停**——它测的是连接规模，而本地三机同在一台物理机，
  5,000 台时宿主机 CPU 打满，结论反映的是宿主机上限（见 [`2026-10-30-ladder-1s.md`](../../test-reports/2026-10-30-ladder-1s.md)）。
  本计划改为连接数固定、只加消息速率，专测消息吞吐。

## 1. 目标

在拆分部署（EMQX 与应用分机）下，固定 1,000 条设备连接，逐档提高每台每秒的发送条数，得出：

1. **可靠无损的最大入库 TPS**——对外承诺只能用它；
2. 各档的接入 QPS（EMQX 收到的 QoS 1 条数/秒）与入库 TPS（InfluxDB 实际写入行数/秒）；
3. 先到瓶颈的是哪一环：EMQX 所在主机、应用主机（transport / Redis / server / InfluxDB）还是发压机。

## 2. 被测环境

| 角色 | 机器 | 内容 |
|---|---|---|
| EMQX 主机 | 本地 VM 128（8 vCPU / 7.7 GB，vmxnet3 网卡） | `deploy/split/emqx`，容器 `conduit-emqx`，容量参数取 EMQX 接受的最大值（inflight 65535、mqueue infinity、关闭 force_shutdown） |
| 应用主机 | 本地 VM 129（8 vCPU / 7.6 GB） | `deploy/split/app`：server、transport ×2（4 连接共享订阅、批 512）、Redis、InfluxDB、PostgreSQL、观测栈 |
| 发压机 | 宿主 Windows（20 核 / 28 线程，31.7 GB） | `docs/script/loadtest/ladder.py`，Python + paho-mqtt |

三者同在一台物理机，彼此争用 CPU 与内存——这是本计划结论的主要局限（见第 7 节）。

## 3. 前置条件（每次执行前逐项确认）

1. **128 上的 AcuCloud 容器全部停止**（8 个：influxdb_v1/v2/v3、xxl-job、rabbitmq、minio、redis、postgres），测完按原清单启动；它们设了自动重启，128 重启后需再停一次。
2. **宿主机腾出 CPU**：关闭 VS Code 的 Java 语言服务（实测空闲时也吃约 2 核）、其他耗 CPU 的程序；宿主机空闲时 CPU 应低于 15%。
3. 演示模拟器照常运行（它已默认排除「压测产品」，不影响守恒核对）。
4. `config.json` 含 `emqx_docker` 与 `ssh.env_file`；`devices.json` 至少 1,000 台（现有 5 万台）。
5. 回读运行配置而不是信仓库：`docker exec conduit-emqx emqx ctl conf show mqtt`（应用主机经 `docker -H` 访问 128）、transport 的批大小与连接数。

## 4. 阶梯

固定 1,000 台设备（devices.json 前 1,000 台），每档建连后稳态保持 300 秒：

| 档 | 每台每秒 | 目标 QPS | 每个发压进程设备数（自动） | 说明 |
|---|---|---|---|---|
| 1 | 2 | 2,000 | 500 | 热身与基准 |
| 2 | 5 | 5,000 | 200 | |
| 3 | 8 | 8,000 | 125 | |
| 4 | 10 | 10,000 | 100 | 2026-10-29 单机部署 3 次全过的速率 |
| 5 | 12 | 12,000 | 83 | 单机部署可靠无损上限约 11,500 |
| 6 | 15 | 15,000 | 67 | 单机部署在 16,000 时 CPU 已满；拆分后应用主机不再跑 EMQX |
| 7 | 18 | 18,000 | 56 | |
| 8 | 20 | 20,000 | 50 | |

每进程设备数按「每进程约 1,000 条/秒」自动分配（`--msgs-per-process`），保证发压程序本身跟得上。

命令（单机执行，首个不合格档即停）：

```bash
cd docs/script/loadtest
python ladder.py run --devices 1000 --rate-plan 2,5,8,10,12,15,18,20 --hold 300
```

预计耗时：每档约 6.5 分钟（建连 + 300 秒 + 排空 30 秒 + 判定），8 档约 55 分钟。

## 5. 判据（任一不满足即不合格）

与 `ladder.py` 一致：

1. 全部设备通过鉴权（首次被拒重连一次后仍被拒才算）；
2. 守恒：客户端 PUBACK 条数 = InfluxDB 实际行数，EMQX 丢弃与死信为 0；
3. 运行中无设备掉线；
4. PUBACK 时延 p99 ≤ 1 秒；
5. 稳态结束时总线积压与 transport 会话队列不超过 5 秒流量；
6. EMQX 无强杀 / 队列满 / emfile，无过载告警（`runq_overload` 等）；
7. **发压机 CPU 平均 ≤ 85%**，超过则本档结果不可信（测到的是宿主机上限），阶梯停止。

## 6. 记录与报告

每档由 `ladder.py` 自动记录：接入 QPS（EMQX 收）、入库 TPS（流水线处理 / InfluxDB 行数）、PUBACK p50/p95/p99/最大、掉线台数与原因、
各发压进程事件循环最长停顿、总线积压峰值、应用主机与 EMQX 主机 CPU、发压机 CPU 平均 / 峰值与可用内存最低。

执行后在 `docs/test-reports/` 写报告：两个数（QPS、TPS）、测试类型、实际命令、每档结果表、瓶颈分析（附失效日志）、与 2026-10-29 单机结果
（可靠无损 11,500 条/秒，600 连接）的对比，以及未执行项。

## 7. 已知风险与局限

- **同一物理机**：发压机与两台 VM 共用 20 核，任一档发压机 CPU 平均超过 85% 即判结果不可信；要测平台本身的上限，需改用同事电脑分担发压
  （`ladder.py` 已支持 `--shard`，同事电脑连 EMQX 需在宿主机做 VMware NAT 端口转发 1883 → 128）。
- 鉴权长连接偶发半开（已立项排查，见 `docs/backlog-v0.2.md`）：只影响建连，`loadgen` 对首次被拒的设备会重连一次。
- `ladder.py` 的 `--rate-plan` 模式只做了离线校验（档位与进程分配计算正确、旧结果可复读），**尚未实跑**；首档即可验证。
- 与 2026-10-29 单机数据不完全可比：当时 600 连接、EMQX 与应用同机、EMQX 信箱 10000 / inflight 1024；现为 1,000 连接、分机、容量参数取最大值。

## 8. 收尾

测试结束后：按清单启动 128 上的 AcuCloud 容器；按需删除 128 上的采样容器 `conduit-probe128`；129 保持现状。
