# 2026-10-30 接收环 4096 对照、鉴权超时放宽与不合格档位复测

承接 [鉴权超时排查](2026-10-30-auth-timeout-investigation.md)，所有者三项决定的执行结果。

## 1. 鉴权超时 5 秒 → 10 秒

`deploy/dev/emqx/base.hocon.tpl` 的 `request_timeout` 改为 `"10s"`（`de5a237`），同步到 EMQX 主机的部署目录后重启 `conduit-emqx`；
回读 `emqx ctl conf show authentication` 为 `request_timeout = "10s"`，重启后 178 条连接、4 个共享订阅恢复。

## 2. 宿主机 CPU 压满下的接收环 1024 / 4096 对照（容量测试的对照实验）

宿主机起 20 个空转进程（空闲 9% → 约 93%，场景开始时 75～80%），同一组场景各跑一次：

| 接收环 | 场景 | 宿主机 CPU | 128 缺缓冲丢包 | 129 缺缓冲丢包 | 鉴权失败 / 僵尸 / 过载告警 | 首次被拒 / 掉线 | p99 / 最大 |
|---|---|---|---|---|---|---|---|
| 1024 | 闲置后 300 台集中建连 | 75% | 0 | 0 | 0 / 0 / 0 | 0 / 0 | 2.2 / 7.3 ms |
| 1024 | 5,000 台 × 每秒 1 条，180 秒 | 77% | **5,911** | 0 | 0 / 0 / 0 | 0 / 0 | 16.2 / 79.0 ms |
| 4096 | 闲置后 300 台集中建连 | 78% | 0 | 0 | 0 / 0 / 0 | 0 / 0 | 2.0 / 19.4 ms |
| 4096 | 5,000 台 × 每秒 1 条，180 秒 | 80% | **0** | 0 | 0 / 0 / 0 | 0 / 0 | 15.7 / 136.3 ms |

接收环 4096 在同等压力下消除了 EMQX 主机的缺缓冲丢包。本次压力（约 80%）未达到事故时的程度（平均 83%、峰值 100%），1024 下的丢包
尚未造成鉴权超时或掉线。改动方式：`ethtool -G <网卡> rx 4096`（128 为 `ens33`、129 为 `ens160`），**运行时生效、重启后恢复 1024**。

## 3. 不合格档位复测（宿主机正常、接收环 4096、鉴权超时 10 秒）

用 `ladder.py` 按全部 7 条判据，每档稳态 300 秒：

| 场景 | 接入 QPS | 结论 | PUBACK = InfluxDB 行 | 入库 TPS | 掉线 / 首次被拒 | p99 / 最大 | 积压峰值 | 应用主机 / EMQX 主机 / 发压机 CPU |
|---|---|---|---|---|---|---|---|---|
| 5,000 台 × 每秒 1 条 | 5,000 | ✅ | 1,499,992 = 1,499,992 | 5,015 | 0 / 0 | 15 / 58 ms | 9,934 | 34% / 42% / 40% |
| 25,000 台 × 每 10 秒 1 条 | 2,500 | ✅ | 749,967 = 749,967 | 2,510 | 0 / 0 | 31 / 1,216 ms | 5,529 | 26% / 32% / 45% |

此前在宿主机紧张时同样两档不合格（5,000 台掉线 403、p99 3.3 秒；2.5 万台掉线约 3,400、p99 9.6 秒）。

命令：`python ladder.py run --plan 5000 --rate 1 --hold 300`；`python ladder.py run --plan 25000 --rate 0.1 --hold 300 --per-process 2500`。
结果目录 `docs/script/loadtest/results/retest-*`（不入库）。

## 结论

- 先前两档的掉线与秒级时延由宿主机紧张造成，宿主机正常时两档均通过；
- 接收环 4096 是有效的保险，能吸收宿主机短暂紧张时的突发；
- 这套本地环境的可靠结论更新为：**每秒 1 条的 5,000 台、每 10 秒 1 条的 2.5 万台均稳定无损**；更高档位未测。
