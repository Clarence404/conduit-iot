# 历史查询文件扫描上限处理计划

- 日期：2026-10-26
- 状态：用户要求暂停（2026-10-26）；仅完成代码与部署配置只读检查，尚未调整参数或修改业务代码。恢复需用户后续指示。
- 优先级：近期修复，第一、二阶段安排在继续 B2 功能开发前；第三阶段纳入 V0.3-E 查询资源治理，实施前补专项设计。

## 已确认的问题

VM 的 InfluxDB 3 Core 返回 HTTP 500：最近 7 天查询需要扫描 432 个 Parquet 文件，超过当前文件扫描限制。数据库健康，近期短范围查询成功。本问题不是 retention 数据保留策略导致。

后端把 InfluxDB 所有 5xx 统一映射为 503「时序库暂不可用」；前端查询失败只弹提示，保留旧曲线，而工具栏已显示新选择的范围，容易误读。

## 第一阶段：演示环境恢复长范围查询

1. 查明 VM 实际启动参数和当前版本 `--query-file-limit` 支持方式、有效值，记录 CPU、内存、文件数量和查询耗时基线。
2. 为开发与独立部署提供可配置的扫描上限，按 VM 容量选择有界值；具体数值待测，不直接无限放大，也不以改 retention 代替处理。
3. 保留现有数据卷，更新 InfluxDB 配置；验证正常上报恢复，并观察内存、CPU、查询延迟及并发影响。
4. 若提高上限后仍因其他限制失败，报告实际原因；不能仅凭容器 healthy 判定通过。

验收：用同一设备的 1 小时、24 小时、7 天、30 天范围（实际只有已有时间段的数据）发起查询，均能返回当前范围的结果；空时间段返回空数据。记录实际参数、扫描数量、响应耗时、资源消耗和回退配置。不能宣称已有完整 30 天数据。

## 第二阶段：错误分类与页面状态

1. 将可识别的文件扫描上限错误映射为稳定业务错误码，给出「查询范围超过数据库限制，请缩短时间范围」；真实连接失败、超时、存储故障仍保留不可用提示。不能向用户暴露 SQL、token 等内部信息。
2. 失败后保留旧曲线时，显式展示「上次成功查询结果」及其真实时间范围，提示本次查询失败；首次加载失败显示可重试状态。
3. 处理切范围、改测点、缩放、自动刷新和并发响应，避免旧响应覆盖新范围；恢复成功后清除过期标记。

验收：分别模拟扫描超限、连接失败、首次加载失败及刷新失败；确认错误分类、旧结果范围、成功恢复与迟到响应处理。补后端/前端测试，并在 VM 实际页面复验。

## 第三阶段：分段查询（V0.3-E）

先设计再实施：长范围分段查询与结果合并，并明确总超时、最大分段数、扫描/并发预算和取消机制。所有分段保持相同租户/设备条件；时间边界用左闭右开，避免丢点或重复。聚合桶使用统一原点，跨段平均值按计数加权，min/max/末值正确合并，不能简单平均各段均值。分段失败须明确整个结果是否完整。不得通过无界分段规避数据库保护。

验收：跨段边界、稀疏点、乱序点、聚合与原始查询、部分失败、跨租户访问，以及长查询与正常短查询并发场景；同一数据集结果与基准一致，查询资源不超出设计预算。
