# 2026-10-30 鉴权回调「长连接半开」排查

## 背景

拆分部署（EMQX 在 VM 128、server 在 VM 129，同一台 VMware 宿主机）下两次出现设备鉴权被拒：EMQX 日志
`http_connector_do_request_failed, reason: timeout`（5 秒），server 端没收到请求；14:02 那次 EMQX 随后判一条鉴权连接为僵尸并重建
（`force_reconnecting_zombie_http_connection`）。当时立项为「鉴权长连接偶发半开」。

## 测试类型

故障排查（取证 + 对照实验），不是性能测试。

## 取证

1. **两端连接表一致，空闲不会造成半开**：闲置约 13 分钟后，EMQX 网络命名空间里 8 条到 129:8091 的连接与 server 容器内的 8 条
   一一对应（同一组端口，队列为空）。8091 经 iptables DNAT 直达 server 容器，不经 docker-proxy。
2. **事故不止一次，都发生在建连突发开头**：13:49:23（3 万台档开始建连，12 次超时）与 14:02:46（闲置后 300 台冒烟，116 次超时，
   同一毫秒批量触发）。
3. **14:02 时 128 被冻结约 3 秒**：128 内采样容器每 30 秒一行，全天唯一一次超过 30 秒的间隔是 14:02:18 → 14:02:51（33 秒）；
   128 内核 14:02:40 `sched: RT throttling activated` 并连续出现内核工作项「占用 CPU 超过 10 毫秒」——虚拟机被宿主机暂停后时钟跳变的典型迹象。
4. **VMware 虚拟网卡在宿主侧丢了大量入站包**：`vmware.log` 中 `VMXNET3 hosted: Cannot retrieve the buffer descriptors per rx packet`
   按分钟计数——13:42 347、13:43 36,574、13:47 300、13:50 31,163、14:02 303（129 同分钟 29）、14:18 2,424，均与建连突发或过载重合。
   客户机内核 `rx_dropped` 为 0，丢包发生在虚拟化层；网卡统计 `pkts rx OOB`（接收环缺缓冲）128 自 13:39 开机累计 401,981、129 为 55,401。
   两台接收环均为 1024（上限 4096）。

## 对照实验（14:51～14:58，宿主机已清理）

清理了宿主机上两个持续占 CPU 的进程（一个空转两天的 Python 残留进程、VS Code Java 语言服务索引已结束）后，**接收环仍为 1024**：

| 场景 | 缺缓冲丢包（128 / 129） | 鉴权请求失败 / 僵尸 | 首次被拒 | 掉线 | p99 / 最大 |
|---|---|---|---|---|---|
| 闲置后 300 台集中建连 | 0 / 0 | 0 / 0 | 0 | 0 | 2.3 / 11.9 ms |
| 5,000 台 × 每台每秒 1 条，180 秒 | 0 / 0 | 0 / 0 | 0 | 0 | 16.2 / 90.8 ms |

同一 5,000 台场景 14:19 时 p99 3.3 秒、掉线 403 台；差别只在宿主机负载。

## 结论

**不是网络连接半开，是宿主机 CPU 紧张导致的虚拟网卡丢包。** 链路：宿主机 CPU 紧张（发压程序 + 两台 VM + 其他程序）→ VM 得不到调度、
短暂冻结 → 客户机来不及补充 vmxnet3 接收环 → VMware 在宿主侧丢弃入站包 → 恰好丢了鉴权请求或回应的 TCP 按指数退避重传，
总等待超过 EMQX 的 5 秒鉴权超时，设备被判未授权；一条连接 10 秒无响应，EMQX 视为僵尸重建。同一机制也解释了 5,000 台档的掉线与秒级时延。
接收环大小只决定能扛多长的停顿，不是根因；宿主机不紧张时 1024 下零丢包。

生产影响：这是 VMware 桌面虚拟化在资源紧张宿主机上的问题，独立服务器或云主机一般不会遇到；但它暴露的「丢包使鉴权超过 5 秒即拒绝设备」
在任何网络都可能发生——设备会重连，不丢数据。
