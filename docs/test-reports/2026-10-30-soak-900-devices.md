# 2026-10-30 900 台设备持续压测：EMQX 文件描述符上限与 CPU 瓶颈

## 被测范围与代码状态

- 代码 `0ade8f2`；VM 配置同 2026-10-29（`max_inflight` 1024、`max_mailbox_size` 10000、`max_mqueue_len` 100000、transport 批 512、4 连接共享订阅）。
- 压测产品 900 台设备（`devices.json` 由 600 补齐到 900），另有模拟器 174 台。

## 测试类型

压力测试（持续过载，刻画失效模式，核对失效日志）。不是容量测试，不产生无损容量结论。

## 命令

- `loadgen.py run --devices 900 --rate 13 --seconds 86400 --workers 24`（目标 11,700 条/秒，计划不停），两轮均人工停止。
- VM 常驻采样器每 30 秒记录各容器 cgroup CPU/内存、整机 CPU 各模式、内存与 swap（`/tmp/prof.jsonl`）；链路指标取自 Prometheus。

## 第一轮（10:36～10:46）：EMQX 反复崩溃重启

开压约 3 分钟后 EMQX 进入崩溃循环，10 分钟内重启 5 次，入库跌近 0，失效日志 50 行。日志：

```
Mnesia('emqx@127.0.0.1'): ** ERROR ** (could not write core file: emfile), ** FATAL ** Cannot open log file ".../PREVIOUS.LOG"
Supervisor: {local,mnesia_kernel_sup}. Context: shutdown. Reason: reached_max_restart_intensity.
```

`emfile` 即打开文件数超限。回读 beam 进程 `/proc/<pid>/limits`：**Max open files 软限制 1024**（Docker 默认）。每条 MQTT 连接占一个描述符，900 + 174 + transport 4 条再加 EMQX 自身文件即超 1024；内置 Mnesia 打不开日志文件，整节点崩溃，设备重连再次打满，形成循环。此前 600 台时连接峰值约 778，未触发。

**影响不限于压测**：按原编排，单个 EMQX 约 1,000 台设备即会反复崩溃。

处置：`deploy/dev/docker-compose.yml` 的 emqx 服务加 `ulimits.nofile` 软硬均 1048576（独立部署包经 extends 继承）；VM 上定点修改后重建 EMQX，回读为 1048576，之后未再崩溃。

## 第二轮（10:48～10:55，修复后）：CPU 饱和、持续丢失

| 指标 | 稳态 |
|---|---|
| EMQX 收（QoS 1） | 约 11,700 条/秒 |
| EMQX 投递给 transport | 3,200～8,800，平均约 6,000 条/秒 |
| 入库 | 约 6,800 条/秒 |
| transport 会话积压 | 12 万～32 万 |
| 连接信箱最大 | 3,217 |
| EMQX 丢弃 | 每 30 秒 0～28,741 |
| 失效日志 | 33 行（连接被强杀） |
| 整机 CPU | 7.5～7.8 / 8 核，其中软中断约 2.5 核 |
| server / transport / Redis / InfluxDB | 约 0.5 / 0.55 / 0.45 / 0.15 核 |
| 可用内存 | 633～1,938 MB |
| 已用 swap | 355 → 937 MB（单次换出 2,724 页/秒），InfluxDB 被换出 544 MB |

**结论**：瓶颈是 CPU，集中在 EMQX 与内核网络处理（合计约 5.9 核，按整机减其余进程推算；本轮采样器未识别重建后的 EMQX 容器名，故无直接值）。平台自身约 1.6 核，在等 EMQX 投递。内存为次要矛盾：swap 持续增长，InfluxDB 首当其冲。

与 2026-10-29 对比：600 连接 11,500 条/秒无损，900 连接 11,700 条/秒明显过载——多出的连接在 EMQX 与内核上有显著开销，吞吐不能直接按「条/秒 ÷ 每台频率」换算为设备数。
