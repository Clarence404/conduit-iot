# Conduit 与 ThingsBoard 同机对照压测（2026-11-14）

**测试类型**：容量测试（逐档加压，看到哪一档仍然无损），同时核对失效日志。

## 结论

同一台 8 vCPU 虚拟机、同一个发压器、同一套判据下的结果：

| 场景 | ThingsBoard 默认（内存队列 + PostgreSQL） | ThingsBoard Kafka + Cassandra | Conduit 独立部署 |
|---|---|---|---|
| 吞吐：1,000 台，每条 3 测点，最高无损档 | **1,000 条/秒**（2,000 不合格） | **3,000 条/秒**（5,000 丢 10%，4,000 未测） | **12,000 条/秒**（11-13 基线；15,000 仍无损，只因 1 次运行队列告警判不合格） |
| 画像：1 万台，每条 30 测点，783 条/秒 | ❌ 处理不过来：入库约 527 条/秒，积压 14.6 万条，停止后 323 秒才排空（最终没丢） | ❌ **丢 48%**：PUBACK 462,078，入库 239,334 | ✅ p99 31 ms，应用主机 CPU 16% |
| 画像：2.5 万台，1,958 条/秒 | 未测（1 万台已不合格） | 未测（1 万台已不合格） | ✅ 服务端全部处理，见下文「2.5 万台判定」；应用主机 CPU 35% |

- **吞吐**：无损吞吐约为 ThingsBoard Kafka + Cassandra 的 4 倍、ThingsBoard 默认部署的 10 倍以上。
- **单条 CPU**：Conduit 8,000 条/秒时应用主机 CPU 42%，即每 1,000 条/秒约 5%。ThingsBoard 默认部署每 1,000 条/秒约 12%，Kafka + Cassandra 约 21%（3,000 条/秒时 64%）。
- **过载时的表现不同**：
  - ThingsBoard 默认规则引擎主队列（Main）的配置是：2 秒处理超时、`SKIP_ALL_FAILURES`。超时的消息直接跳过，**已经回了 PUBACK 的数据会静默丢失**。日志可见：Kafka + Cassandra 5,000 条/秒档有 785 行以上 `Timeout to process message`，画像档有 3,034 行。
  - Conduit 过载时先积压在总线中，不会因超时而丢弃；丢数只会在 EMQX 会话队列满时发生，并且可以从计数器看到（11-13 基线 18,000 条/秒档）。
- **口径限制**：
  - ThingsBoard 两种部署都用官方默认参数，没有调优。改成重试策略、加长超时可以避免跳过丢数，代价是积压。
  - ThingsBoard 官方容量数据用的是更大的机型，每条约 3 个测点，见第 5 节。
  - 本报告的数字只代表这台本地虚拟机，**不得外推**到物理机或云主机。

## 1. 环境

**被测机**：压测虚拟机，8 vCPU（i7-14700，VMware）、11.4 GB 内存 + 2 GB swap、vmxnet3 网卡、Rocky Linux 10.2。
- 两个平台在同一台机器上**轮流运行，不同时运行**。
- 发压器在开发机上（宿主机 20 核 / 28 线程、32 GB）。

**ThingsBoard 默认部署**
- `thingsboard/tb-node:4.3.1.8`（单体，`-Xms4g -Xmx4g`）+ `postgres:18`。
- 队列为内存队列，时序与最新值都存 PostgreSQL。
- 使用 Demo 租户，租户配置没有限流。

**ThingsBoard Kafka + Cassandra**
- `tb-node:4.3.1.8`（堆 4 GB），配置 `TB_QUEUE_TYPE=kafka`、`DATABASE_TS_TYPE=cassandra`、`DATABASE_TS_LATEST_TYPE=cassandra`。
- 依赖：`bitnamilegacy/kafka:4.0`（堆 1 GB）、`cassandra:4.1`（堆 2 GB）、`postgres:18`（实体数据）。
- 这是官方建议在约 3～5k 数据点/秒以上使用的组合。

**Conduit 独立部署**（`deploy/standalone`）
- 镜像：server 构建于 10-30，transport 构建于 11-12，与 11-13 基线是同一套。
- EMQX 参数取仓库默认值：`max_inflight` 512、批 64、`max_mqueue_len` 50000、信箱 10000。
- 测试期间临时把 129 上漂移的 `.env` 改回仓库默认值，测完已恢复拆分部署。

**两边一致的条件**
- 设备逐台建好。Conduit 走 `conduit/{pk}/{dk}/up/property`，ThingsBoard 走 `v1/devices/me/telemetry`。
- QoS 1，MQTT 3.1.1 / 5。
- Conduit 关闭可靠上报，因为 ThingsBoard 没有业务回执。

## 2. 方法与判据

**发压**：`docs/script/loadtest/ladder.py` 与 `loadgen.py` 的 fleet 模式。ThingsBoard 部分由 `tb_bench.py` 负责建设备、调用 ladder、数行、采样容器指标。

**吞吐档（方法 1）**
- 1,000 台，每台每秒 N 条，每条 3 测点，稳态 300 秒。

**画像档（方法 4）**
- 每条 30 测点，设备上报频率混合：70% 每 60 秒 1 条、25% 每 15 秒 1 条、5% 每秒 1 条。平均每台 0.0783 条/秒。
- 1 万台和 2.5 万台各稳态 600 秒，每个发压进程负责 2,500 台。

**合格判据**（两边相同，不满足任一条即不合格）
1. 计数守恒：PUBACK 数等于库中行数。
   - Conduit 数 InfluxDB 的行数。
   - ThingsBoard 数 `ts_kv` 中 `Ua` 键的行数：默认部署查 PostgreSQL，Kafka + Cassandra 部署在 Cassandra 中逐设备查询。
2. 运行中没有设备掉线。
3. p99 ≤ 1 秒。
4. 结束时积压不超过 5 秒的流量：
   - Conduit 看 Redis 消费组的滞后与待确认数之和。
   - ThingsBoard 默认部署按「已确认数减已入库行数」计算。
   - Kafka + Cassandra 看消费组滞后。
5. 结果可信：发压进程占用不超过单核的 85%，宿主机平均 CPU 不超过 85%。

## 3. 结果

### 3.1 ThingsBoard 默认部署（内存队列 + PostgreSQL）

| 设备数 | 消息/秒 | 结论 | PUBACK / ts_kv 行 | p50 / p99 ms | 结束积压 | 排空秒 | 应用主机 CPU% | tb-node CPU% / MiB | PostgreSQL CPU% / MiB | 原因 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 1,000 | ✅ | 299,998 / 299,998 | 1.8 / 39 | 0 | 0 | 12.4 | 38 / 3,938 | 25 / 228 | - |
| 1,000 | 2,000 | ❌ | 599,989 / 599,957 | 4.1 / 369 | 32 | 0 | 24.0 | 75 / 3,974 | 71 / 226 | 少 32 行 |
| 10,000 | 783（30 测点） | ❌ | 462,079 / 462,079 | 4.4 / 386 | 145,909 | 323 | 22.6 | 74 / 5,350 | 65 / 231 | 积压超过 5 秒流量（3,917） |

- **2,000 条/秒档少的 32 行，原因无法拆分。** 当时日志中有主队列超时（跳过即丢），同时发压循环最长卡顿 0.54 秒，超过了 0.5 秒的发送间隔，可能产生同 ts 消息被覆盖（见 3.4）。保守起见判为不合格。
- **画像档没有丢数，但处理能力跟不上。** 入库只有约 527 条/秒，约等于 1.6 万数据点/秒。由于不合格，2.5 万台档没有运行。

### 3.2 ThingsBoard Kafka + Cassandra

|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 1,000（冒烟 60 秒） | ✅ | 59,998 / 59,998 | 5.3 / 31 | 0 | 61.3 | 251% / 3,756 | 86% / 1,132 | 165% / 2,637 | - |
| 1,000 | 1,000 | ✅ | 299,999 / 299,999 | 3.2 / 15 | 0 | 35.8 | 144% / 3,863 | 58% / 1,161 | 103% / 2,918 | - |
| 1,000 | 2,000 | ✅ | 600,000 / 600,000 | 3.2 / 13 | 0 | 55.7 | 222% / 4,000 | 81% / 1,199 | 155% / 3,368 | - |
| 1,000 | 3,000 | ✅ | 899,989 / 899,989 | 3.6 / 19 | 0 | 63.8 | 261% / 4,137 | 79% / 1,225 | 144% / 3,556 | - |
| 1,000 | 5,000 | ❌ | 1,499,990 / 1,350,387 | 4.0 / 109 | 0 | 64.8 | 275% / 4,866 | 47% / 1,236 | 152% / 3,468 | 丢 149,603（10.0%） |
| 10,000 | 783（30 测点） | ❌ | 462,078 / 239,334 | 8.2 / 81 | 0 | 40.8 | 213% / 4,917 | 16% / 1,064 | 107% / 3,574 | 丢 222,744（48.2%） |

（tb-node、Kafka、Cassandra 三列均为「CPU% / 内存 MiB」。）

**丢数的成因**
- 这两档 Kafka 滞后都是 0：消息已被规则引擎取走，但在 2 秒内没能完成时序写入，于是按 `SKIP_ALL_FAILURES` 被跳过。
- 日志中 `Timeout to process message: TbMsg(queueName=Main…)` 的出现次数：5,000 条/秒档 785 次以上，画像档 3,034 次，另有大量 `Timeout to process [N] messages` 汇总行。
- 发压循环最长卡顿仅 0.02～0.06 秒，**可以排除工具原因**。

**画像档为什么比纯吞吐更差**
- 每条 30 测点意味着 Cassandra 要写约 2.3 万行/秒，而吞吐档只要约 1.5 万行/秒。
- ThingsBoard 逐条消息等待全部测点写完，所以测点多时更容易超时。

**冒烟档 CPU 偏高**：冒烟档的应用主机 CPU 高于 1,000 条/秒的正式档，原因是刚建完 2.5 万台设备、JVM 尚在预热。

### 3.3 Conduit 独立部署

**吞吐档**（11-13 基线，同一台虚拟机，`docs/test-reports/2026-11-13-standalone-session-limits.md`）

| 消息/秒 | 结论 | p99 ms | 应用主机 CPU% |
|---|---|---|---|
| 8,000 | ✅ | 13 | 42 |
| 10,000 | ✅ | 14 | 45 |
| 12,000 | ✅ | 20 | 59 |
| 15,000 | ❌ 仅因 1 次运行队列告警，守恒成立 | 185 | 73 |
| 18,000 | ❌ 会话队列满，丢弃 47.5 万条 | - | - |

**画像档**（本轮新测）

| 设备数 | 消息/秒 | 结论 | PUBACK / InfluxDB 行 | 入库 TPS | 掉线 | p99 ms | 积压峰值 | 应用主机 CPU% | 发压进程最忙单核% / 合计核 | 宿主机 CPU% 平均 / 峰值 |
|---|---|---|---|---|---|---|---|---|---|---|
| 10,000 | 783 | ✅ | 462,074 / 462,074 | 788 | 0 | 31 | 1,379 | 16 | 30 / 1.2 | 15 / 42 |
| 25,000 | 1,958 | ✅（见下） | 1,140,112 / 1,137,122 | 1,917 | 0 | 44 | 9,273 | 35 | 49 / 4.5 | 35 / 86 |

**2.5 万台判定**
- 按行数比对，脚本当时判为「守恒不等」，差 2,990 行。逐项核对后，确认这是发压工具的问题，不是丢数：
  - EMQX 的 `emqx_messages_qos1_received` 增量与 server 的 `conduit_pipeline_processed_total{type="property"}` 增量**都是 1,151,857**。差额 11,745 是同时运行的演示模拟器的流量（1 万台档的差额同为 11,484）。服务端对每一条都写入成功后才计数。
  - EMQX 丢弃数为 0，死信为 0，期间 server 没有重启。
  - 发压循环在负载开始约 20 秒时整体卡顿了 3.5 秒。补发时，同一轮循环共用同一个 `now` 作为 ts，于是 5% 每秒发 1 条的设备（1,250 台）每台出现 2～3 条同 ts 的消息。估算重复约 2,500～3,750 条，与 2,990 吻合。
  - InfluxDB 按（序列, ts）幂等覆盖，同 ts 的多条只留一行。
- 处置：`loadgen.py` 的 fleet 模式已改为同设备的 ts 严格递增，补发时顺延 1 ms。修正后尚未复测。

### 3.4 对其他已有结果的影响

- 只有发压循环卡顿超过某台设备的发送间隔时，才会产生同 ts 消息。
- 本轮受影响的只有两档：Conduit 2.5 万台（3.5 秒卡顿），以及 ThingsBoard 默认部署 2,000 条/秒（0.54 秒卡顿，间隔 0.5 秒）。
- 其余各档的最长卡顿都小于发送间隔。

## 4. 架构层面的解读

- **ThingsBoard 的瓶颈在逐条消息处理**：每条消息都要走规则引擎（消息对象创建、规则链、actor 投递），时序写入按消息等待完成。Kafka + Cassandra 让持久化与扩展更好，但在同一台 8 核机器上，4 个 JVM 互相争抢 CPU 与内存，单机吞吐反而受限。
- **Conduit 的热路径是批处理**：transport 微批写入 Redis Streams，server 批量解码、一次写 InfluxDB、Redis 走 pipeline。热路径上没有规则引擎。

**这个对比不等于「Conduit 全面更快」。**
- Conduit 目前还没有规则引擎与告警（V0.5）。规则引擎接入后，热路径的开销会增加。
- ThingsBoard 的能力面更完整，并且官方支持集群。

**可靠性语义**
- ThingsBoard 默认的「超时跳过」意味着过载时已确认的数据会静默丢失，必须在队列设置里改为重试策略，才能保证不丢。
- Conduit 的默认语义是至少一次，丢弃有计数器可查。

## 5. 与官方数据的关系

ThingsBoard 官方性能测试：单体部署，每条约 3 个数据点，连续运行 24 小时以上。

| 实例 | 设备数 | 消息/秒 | CPU |
|---|---|---|---|
| c5.xlarge（4 vCPU） | 10 万 | 1,111 | 20% |
| c5.4xlarge（16 vCPU） | 50 万 | 5,555 | 40% |

**与本次结果的对照**
- 官方数据侧重大量设备、低频上报。本次吞吐档是 1,000 台高频上报，画像档每条 30 个测点，两者不能直接换算。
- 本次 ThingsBoard 默认部署 1,000 条/秒时 tb-node 占 38% 单核、主机 CPU 12%，与官方 4 vCPU 跑 1,111 条/秒的量级相符。由此看，**本次部署没有明显的配置失误**。

## 6. 跳过、阻塞与遗留

- **未测的档位**
  - ThingsBoard Kafka + Cassandra 的 4,000 条/秒，没有逐档细分。
  - 两种 ThingsBoard 部署都没有跑 2.5 万台画像档，因为 1 万台已经不合格。
  - 没有测试调优后的 ThingsBoard（主队列改重试、加长超时、加大 Cassandra 并发），结论只代表默认配置。
- **Conduit 2.5 万台画像档**：修正 ts 后尚未复测，当前判定依据是服务端计数。
- **ThingsBoard 两套环境的现状**：在压测机上保留为已停止状态，包括 `/opt/tb-bench`、`/opt/tb-bench-kc` 与数据卷。这两套环境与 Conduit 无关，是否删除待所有者决定。
- **运行状态**：测试结束后，压测机已恢复拆分部署，并核对过：EMQX 主机 inflight 1024 / mqueue 50000 / 信箱 10000，178 条连接，4 个共享订阅，transport-2 为 LEADER 且 connected，总线积压 9。

## 7. 复现

```bash
# ThingsBoard（需要先在压测机上部署 ThingsBoard，并在 config.json 中指向压测机）
python docs/script/loadtest/tb_bench.py provision --devices 25000
python docs/script/loadtest/tb_bench.py run --plan 1000 --rate-plan 1,2,3,5 --hold 300 --out results-tb-throughput
python docs/script/loadtest/tb_bench.py run --plan 10000,25000 --hold 600 --mix 60:0.7,15:0.25,1:0.05 --points 30 --per-process 2500 --out results-tb-profile
# Kafka + Cassandra 部署：在上面的命令前加 TB_STACK=kc

# Conduit 独立部署画像
python docs/script/loadtest/ladder.py run --plan 10000,25000 --hold 600 --mix 60:0.7,15:0.25,1:0.05 --points 30 --id-ratio 0 --per-process 2500 --out results-sa-profile
```

结果目录 `docs/script/loadtest/results-*` 不入库。逐档 JSON 与判定 JSON 保存在开发机上。
