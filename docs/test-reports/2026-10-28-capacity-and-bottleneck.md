# 容量与瓶颈压测报告：阶梯加压至失效

- 日期：2026-10-28（Asia/Shanghai）
- 被测版本：`2a54424`（关闭磁盘持久会话 + transport 微批 + 会话监控之后）
- 环境：压测机 192.168.126.129，Rocky Linux 10.2、8 核、7.5 GB 内存、16 GB 磁盘，standalone 栈 11 容器
- 负载端：开发机 Python + paho-mqtt，每设备一条 MQTT 连接，QoS 1、不带消息 id
- 目的：逐级加压直到某个环节失效，定位整体瓶颈
- 结论：**出口侧（transport → Redis → 流水线 → InfluxDB）在 4,000～5,000 条/秒饱和；入口侧可吃到约 8,900 条/秒。超出部分堆积在 EMQX 队列中，队列填满后触发三段级联失效，但系统自行恢复，无需人工干预。**

## 1. 阶梯结果

每级 600 台设备以内、持续 120 秒，之后观察排空。

| 目标（条/秒） | 客户端发出/秒 | EMQX 确认/秒 | mqueue 峰值 | 宿主机可用内存 |
|---|---|---|---|---|
| 2,000 | 2,002 | 2,002 | 0 | 2,286 MB |
| 3,000 | 3,080 | 3,080 | 1,710 | 1,628 MB |
| 4,500 | 4,529 | 4,525 | 4 | 1,327 MB |
| 6,000 | 5,938 | 5,932 | 9,347 | 918 MB |
| 9,000 | 8,892 | 8,881 | **100,000（触顶）** | 1,128 MB |

**客户端发出与 EMQX 确认在每一级都几乎相等**，说明接入侧直到 9,000 条/秒都没有成为瓶颈。

## 2. 最重要的发现：PUBACK 不等于平台收下了

目标 9,000 时，EMQX 确认了 8,881 条/秒，同时在丢弃：

```
clientid: conduit-transport, msg: dropped_msg_due_to_mqueue_is_full,
queue: #{len => 100000, dropped => 38566, max_len => 100000}
[warning] log_events_throttled_during_last_period, dropped: #{dropped_msg_due_to_mqueue_is_full => 38564}
```

本轮累计丢弃 **51,671 条**。

**EMQX 先向设备回了 PUBACK，之后才把消息丢掉。** 这符合 MQTT 语义——PUBACK 表示 broker 已接收，不表示订阅端已取走——但后果对设备是不可见的：

> 过载时，**不携带消息 `id` 的设备会收到 QoS 1 确认，而数据并未进入平台**，且设备无从得知。

这为 2026-10-28 写入设备接入契约的那句「不携带 `id` 的上报只有逐跳的 QoS 1 保证」提供了具体、可复现的证据。携带 `id` 的设备不受影响：平台的业务回执是在写入消息总线成功之后才发的，队列丢弃的消息永远拿不到回执，设备会重发。

## 3. 失效链条（三段级联）

目标 9,000 条/秒下按时间顺序发生：

**第一段 — 连接进程信箱溢出被关闭**

```
msg: check_oom_shutdown
shutdown: #{max => 1000, reason => mailbox_overflow, value => 2615}
policy: #{max_heap_size => 33554432, enable => true, max_mailbox_size => 1000}
```

原因是 **`mailbox_overflow`（信箱 2615 条 > 上限 1000），不是堆超限**。`force_shutdown.max_mailbox_size` 默认 1000，此前未被注意到。

**第二段 — mqueue 填满并开始丢弃**

队列达到上限 100,000，一分钟内丢弃 38,564 条。

**第三段 — 持有满队列的新连接进程超堆被杀**

```
maximum heap size reached
Max Heap Size:   50331648 字（384 MB）
Total Heap Size: 67278065 字（513 MB）
Kill: true
```

**系统随后自行恢复**：transport 重连、建立新会话、继续工作。全程无容器重启、无宿主机 OOM、无人工干预。

| | 2026-10-27 磁盘持久会话故障 | 本次（内存会话） |
|---|---|---|
| 触发 | 入库慢于接入即可 | 需持续过载至队列填满 |
| 表现 | 投递永久冻结，所有信号为绿 | 丢弃有计数、有日志 |
| 恢复 | **不可能**，只能丢弃会话与积压 | **自动恢复** |
| 重启 transport | 触发重放超堆死循环 | 不适用 |

## 4. 已回答的遗留问题：10 万条 mqueue 确实撑爆 384MB 堆

[2026-10-28 修复验证报告](2026-10-28-session-wedge-fix-verification.md)中记录为「未取得」的那项数据，本次取得了：

**队列填满 100,000 条时，会话进程堆达到 513 MB，超过 384 MB 上限并被杀。** 折合每条消息约 **5.4 KB** 的 Erlang 堆开销，而消息载荷仅约 60 字节。

因此当前默认 `EMQX_MAX_MQUEUE_LEN=100000` **偏大**：队列一旦填满，连接进程即被杀、整个队列丢失。

这造成一个需要决策的张力：

| 约束 | 要求的队列容量 |
|---|---|
| 覆盖 transport 主备切换窗口（约 17 秒 × 峰值 4,300 条/秒） | 约 73,000 |
| 不撑爆 384 MB 堆（按 5.4 KB/条、留 50% 余量） | 约 35,000 |

两者冲突，需在「切换期间少丢」与「队列满时不触发进程被杀」之间取舍。**待所有者决策，本报告不擅自更改配置。**

## 5. 瓶颈定位

| 环节 | 观测 | 是否瓶颈 |
|---|---|---|
| 客户端 | 发出与确认几乎相等，最高 8,892 条/秒 | 否 |
| EMQX 接入 | 确认 8,881 条/秒，CPU < 1% | 否 |
| **出口侧**（transport 攒批 → Redis → 流水线 → InfluxDB） | 队列峰值随负载单调增长，9,000 时触顶 | **是，饱和于 4,000～5,000 条/秒** |
| CPU | 各容器全程 < 1% | 否 |
| 磁盘空间 | 全程稳定 9.6 GB 可用 | 否 |
| 内存 | 2,286 → 918 MB，失效后回升至 1,128 MB | 接近但未触底 |

出口侧的三个候选成因（**本次未分别定量，属未完成项**）：

1. **Redis `appendfsync always`** —— 每次写入等待 fsync。
2. **transport 单线程投递**，批大小受 `max_inflight=32` 限制。
3. **InfluxDB WAL 刷盘间隔 1 秒** —— 已知「吞吐 ≈ 批大小 ÷ 1 秒」。

## 6. 方法缺陷与自我更正（如实记录）

**缺陷一：Redis 流长度指标作废。** 脚本采集了 `XLEN conduit:stream:up`，但该流有 `MAXLEN` 100 万上限，全程被裁剪、读数恒在 1,000,000 附近，无法反映入库进度。这一列数据作废。**同一个坑在 2026-10-27 的压测中已经踩过一次，本次写脚本时重犯。** 正确做法是用消费组的 `entries-read` 或 InfluxDB 实际行数。

**缺陷二：各级「投递/秒」不可用。** 脚本按固定的 165 秒（120 加压 + 45 排空）折算速率，而客户端实际耗时远超于此（断开 600 条连接时要处理各自积压），因此该列系统性偏高；9,000 一级因会话计数器重置甚至出现负值。表 1 中已剔除该列，仅保留可信的发出/确认/队列峰值。

**更正一：** 测试过程中我曾判断「系统在约 2,000 条/秒即开始反压上游」。**该判断错误**，来自单次测量。阶梯数据显示 EMQX 一路确认到 8,881 条/秒。

**更正二：** 我曾判断「入口不会失效，系统靠 PUBACK 反压挡住多余流量」。**该判断错误且方向相反**——EMQX 并不向发布端反压，而是照常 PUBACK 然后在订阅队列满时丢弃（见第 2 节）。先前描述的反压机制只存在于 EMQX → transport 一跳，不存在于设备 → EMQX 一跳。

## 7. 未执行与限制

- **出口侧三个候选成因未分别定量**：未单独测量 Redis fsync 延迟、未试 `appendfsync everysec` 对照、未调整 InfluxDB WAL 刷盘间隔做对照。这是确定「4,000～5,000 条/秒由谁决定」的关键实验，尚未进行。
- **未做 `max_inflight` / `batch-size` 成对上调**（64 / 256 / 1024）的吞吐阶梯。
- **未测最大连接数**：本次最多 600 条并发连接，瓶颈在速率而非连接数。
- **未做长时间浸泡**：压测机磁盘仅 16 GB。
- 每级仅一次采样，绝对值有波动：同一配置在不同轮次测得 1,980 与 2,640 条/秒，相差 33%。**本报告的速率应按区间理解，不应作为单点承诺。**
- 失效后对已丢弃消息的入库缺口未做逐条核对，仅依据 EMQX 的丢弃计数。

## 8. 环境状态

测试结束后 11 个容器全部正常，无重启、无 OOM，模拟器已恢复。宿主机可用内存 865 MB、磁盘 9.5 GB。
