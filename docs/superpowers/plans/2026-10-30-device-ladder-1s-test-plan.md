# 测试计划：N 台设备 × 每台每秒 1 条（连接规模阶梯）

- 状态：**暂停，保留作后期对比**（所有者 2026-10-30 决定）。当前先执行
  [1,000 台设备逐档提速测 QPS / TPS](2026-10-30-qps-tps-1k-devices-test-plan.md)。
- 测试类型：容量测试（找无掉线、时延达标、积压不增长的最大设备数）。
- 已有结果：[`2026-10-30-ladder-1s.md`](../../test-reports/2026-10-30-ladder-1s.md)——2,000 台通过；5,000 台不合格（403 台掉线、p99 3.3 秒），
  复现取证表明根因是发压机与两台 VM 同在一台物理机、宿主机 CPU 打满，结论反映的是物理机上限而非平台上限。

## 1. 与 QPS / TPS 测试的区别

| | 本计划（连接规模） | QPS / TPS 计划（消息吞吐） |
|---|---|---|
| 变量 | 设备数 N 逐档增加，每台每秒 1 条 | 设备数固定 1,000，每台每秒条数逐档增加 |
| 回答的问题 | 平台能同时承载多少台「每秒报一次」的真实设备 | 平台每秒能接收并入库多少条消息 |
| 主要成本 | 每台设备一条连接、每条消息单独一次网络往返——EMQX 每条消息的 CPU 约为少量连接批量发送时的 4 倍 | 连接少，成本主要在消息处理与入库 |

两者结合才能回答「多少台设备、每台多久报一次」能撑住：例如 QPS / TPS 测试得到入库上限 T，本计划得到在每秒 1 条下的最大设备数 N，
二者的差距就是连接数带来的额外开销。

## 2. 环境与前置条件

与 QPS / TPS 计划相同（拆分部署：EMQX 在 VM 128，应用在 VM 129；停 128 上的 AcuCloud 容器；腾出宿主机 CPU；回读运行配置）。
**额外要求：发压程序必须放在另一台电脑**（或多台同事电脑分担，`ladder.py --shard`）——单台宿主机在 5,000 台时已打满，
不分机重跑只会得到同样的物理机上限。同事电脑连 EMQX 需在宿主机做 VMware NAT 端口转发 1883 → 128，或把 128 改为桥接网卡。

每档建连后稳态 300 秒；每个发压进程负责 1,000 台（每进程约 1,000 条/秒）。

```bash
# 单台发压机（仅作对照，结果受物理机限制）
python ladder.py run --plan 2000,5000,8000,10000,12000,15000,18000,20000 --rate 1 --hold 300
# 三台电脑分担（各机同一组参数、不同 --shard，约定同一开始时刻），结束后合并判定
python ladder.py run --plan 2000,5000,8000,10000,12000,15000,18000,20000 --rate 1 --hold 300 --start-at 15:00 --shard 1/3
python ladder.py check results-a results-b results-c
```

## 4. 判据

与 `ladder.py` 一致的 7 条：全部鉴权通过；PUBACK = InfluxDB 行数且丢弃、死信为 0；无运行中掉线；p99 ≤ 1 秒；积压不超过 5 秒流量；
EMQX 无强杀 / 过载告警；发压机 CPU 平均 ≤ 85%（多机时取各机最大值）。
