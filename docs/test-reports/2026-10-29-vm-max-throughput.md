# 压测 VM 不崩溃的最大吞吐

- 日期：2026-10-29（Asia/Shanghai）
- **测试类型**：容量测试（守恒判据下找最大无损速率）+ 压力测试（越过上限、核对失效日志）+ 主备切换故障注入
- 目标（所有者要求）：在这台 VM 上求「不崩溃的最大吞吐」，代码与配置按此取舍
- 取代：[`2026-10-29-capacity-after-batching.md`](2026-10-29-capacity-after-batching.md) 的容量结论（已在其头部标注作废）

## 1. 结论

| | 入库 TPS（= 接入 QPS） | 依据 |
|---|---|---|
| **可靠无损** | **11,500 条/秒** | 2 次全部守恒通过 |
| 可靠无损（含故障注入） | 10,000 条/秒 | 3 次全部通过，其中 1 次在负载下强杀主 transport |
| 边缘 | 13,000 条/秒 | 3 次中 2 次通过 |
| 硬件墙 | 16,000 条/秒 | VM 8 核整机 CPU 96～97%、1 分钟负载 15 |

接入 QPS 与入库 TPS 在通过的档位上**完全相等**——判据本身就要求五个计数口径一致，所以这里不存在「接入高、入库低」的差额；失败档位两者的差额就是丢失量。

**墙已从软件移到硬件。** 16,000 条/秒时 8 个 vCPU 全满、运行队列约为核数的两倍，各组件抢 CPU，
transport 与 EMQX 跟不上而连接被杀。13,000 时 CPU 约 92%，任何周期性的额外负载（失败那次 InfluxDB
写入耗时由平时约 640ms 升到 1,056ms）都足以越线。再往上只能降低每条消息的 CPU 开销或加核。

**对比**：当天早上可靠无损只有 5,000（2.3 倍）；前一份报告的「可持续 6,600」不成立（见第 3 节）。

## 2. 起作用的改动（按效果排序）

| 提交 | 改动 | 效果 |
|---|---|---|
| `65ad9a2` | transport 主实例开 4 条连接、共享订阅分摊 EMQX 投递 | **主因**。拆掉 EMQX 单连接进程的单核天花板 |
| `141bdd6` | 写最新值前合并同批被完全覆盖的数据点 | 10,000 档 `latest` 阶段 1,856ms → 98ms，周期 3,367ms → 942ms |
| 配置 | EMQX `max_mailbox_size` 1000 → 10000 | 修正 VM 上 inflight 1024 大于信箱上限的错误配置 |
| `f12ee25` | 流水线 4 个消费者并发；在线状态改用 EVALSHA | 去掉单线程等刷盘；单独测不出可分辨的收益（见 4.4） |

**做了但被证明无效或有害的**：WAL 刷盘间隔 1s → 100ms（吞吐反降 36%，已回滚）；最新值 Lua 快路径
（`f73f4e8`，收益落在噪声内，脚本正确、保留）。

## 3. 推翻前一份报告的两处测量缺陷

**一、实际供给比名义目标低 1/6。** 压测产品带物模型，演示模拟器按 `SIM_TENANTS=*` 给其前
`SIM_MAX_DEVICES_PER_PRODUCT`（100）台设备重置了密钥，`devices.json` 中那 100 台静默鉴权失败
（paho 的 `connect()` 不等 CONNACK，鉴权被拒不抛异常）。名义 10,000 实际只喂进 8,333，EMQX 恰好收到
8,334——所谓「约 8,300 入口天花板」就是供给本身。特征：**接入量永远恰好是名义目标的 5/6**，真实上限
是绝对值、不会按比例缩放。工具修复：`67a785b`（`run` 等 CONNACK，未通过即退出；新增 `refresh`）。

**二、只记速率峰值，从未做计数守恒。** 速率证明不了不丢：过载时 EMQX 先 PUBACK 再丢弃，入库 TPS 照样不低。

## 4. 定位过程（含全部弯路）

### 4.1 守恒判据

每档比对五个独立口径必须相等：客户端 publish 数、客户端 PUBACK 数、`emqx_messages_received` 计数差、
`conduit_pipeline_processed_total{type="property"}` 计数差、**InfluxDB 实际行数**（直接 SQL，不经应用
内存计数器）。同时要求 `emqx_messages_dropped` 增量、死信增量、EMQX 失效日志均为 0。

判据本身踩过的坑（都已修正）：

- 失效日志锚点不带 `Z`：VM 为 CST，Docker 按本地时间解释，多截 8 小时，把 0 次数成 295 次。
- 固定等待 120 秒排空：高档位积压可达百万条，会把「没排完」判成「丢了」。改为等入库计数停增。
- 「失效次数」数的是日志**行数**：每次强杀打两行，还混入 `mqueue_is_full`。本报告中的「失效 N」约等于 N/2 次强杀。

### 4.2 先修信箱：无损上限 3,000～5,000 → 约 7,000

信箱 1000 时：3,000 两次通过，5,000 三次中两次丢消息（丢失率 0 / 1.55% / 4.8%）。强杀日志：

```
clientid: conduit-transport, msg: check_oom_shutdown,
shutdown: #{max => 1000, reason => mailbox_overflow, value => 1106}
```

调为 10000 后 5,000、7,000 通过，9,000 失败（入库 889,248，约 7,410 条/秒到顶）。

**更正**：当时据仓库与 `CLAUDE.md` 判断「inflight 512 对信箱 1000 只有 2 倍余量」。事后查明 **VM 实际运行
的是 inflight 1024**——VM 的 compose 与 `.env` 落后于仓库，2026-10-28 的 1024→512 修正从未部署到这台机器。
1024 > 1000 正是 `CLAUDE.md` 早已记载的「必然溢出」配置。调大信箱实际是在修正这个错误配置。

### 4.3 流水线分阶段计时：两条规律

新增指标 `conduit.pipeline.stage{stage=total|identity|decode|influx|latest|ack}` 与 `conduit.pipeline.batch.size`
（提交 `aad561f`、`f9ce957`）。首次测量得出「子阶段大于总耗时」，根因是分母不一致：total 把数千个只含
上下线事件的微批也算进均值（样本 3,237 个，influx 仅 528 个）。改为 total 只在属性批记录后自洽。

信箱 10000、单消费者、WAL 1s 时：

| 目标 | 每批条数 | 总耗时 | influx | latest | 其余 | 结论 |
|---|---|---|---|---|---|---|
| 5,000 | 5,357 | 1,018ms | 616 | 259 | 127 | 通过 |
| 7,000 | 10,633 | 1,430ms | 633 | 506 | 260 | 通过 |

- `influx` **几乎不随批大小变化**（批翻倍、616→633ms）：它在等 WAL 刷盘，不是在传数据。
- `latest` **随批大小线性增长**（约 48µs/条）。

### 4.4 三个没起作用的改动

**WAL 刷盘 1s → 100ms（负优化）**：influx 降到约 79ms，但批从约 1 万条缩到约 1,700 条，每批约 120～260ms
的固定开销摊不薄，吞吐 7,434 → 4,721。7,000 / 9,000 / 11,000 三档全败。**那 1 秒等待在攒批，不是浪费。**

**Lua 快路径**（ts ≥ `__last` 时跳过逐测点比较）：5,000 档两次 41.7 / 46.7 µs/条，对基线一次 48.3。
自身波动 12% ≥ 与基线差距 8%，**测不出收益**。脚本经压测机 Redis 新旧差分测试八个用例全部等价，保留。

**流水线 4 消费者并发**：7,000 失败。当时推断「流水线抢了 transport 的 Redis」，实测 Redis 单线程仅 20%，
**推断错误**。7,000 在单消费者时就是「过、败、过、过、败」，单次结果本就说明不了什么。

transport 批 64 → 512：EMQX 丢弃归零，但连接仍被强杀。

### 4.5 直接证据：墙在 EMQX 单连接进程

用 EMQX 自带的 `recon`，9,000 条/秒、3 秒窗口：

| 进程 | reductions |
|---|---|
| transport 连接进程 | 15,243,392 ～ 18,054,191 |
| 任一设备连接进程 | 约 46,000 |

transport 进程约为单个设备连接的 350 倍、占 EMQX 全部工作约 35%；8 个调度器整体仅 41～48%，该进程
已顶在单调度器上限。**此前对流水线和 transport 批大小的优化都在它下游，所以都看不到效果。**

这也说明前一天撤回「单连接是瓶颈」撤得太宽：8,300 是假的，结构问题是真的。

### 4.6 共享订阅快速验证（不进仓库）

停掉 transport，换成只回 PUBACK 的探测订阅者，14,000 条/秒 × 90 秒：

| K | EMQX 收 | 订阅端实收 | 丢弃 | 强杀 |
|---|---|---|---|---|
| 4 | 1,259,995 | 1,259,995（100%） | 0 | 0 |

K=1 那组只收 374 条/秒，**不作数**：EMQX 内该连接进程未进消耗前 6 名、信箱为 0，是 Python 探测客户端自身扛不住。

首轮探测订阅者**全部连不上**（`sub_procs=0`）——transport 超级用户鉴权要求 clientId 以 `conduit-` 开头，
而脚本也犯了不等 CONNACK 的同一个错，靠「订阅端实收 0」才看出来。

安全性（持久会话的共享组成员离线时消息去哪）：全员离线后重连补收 6,000/6,000；4 个中 1 个离线时其会话
排队、重连补收，合计 5,999/5,999，丢弃均为 0。

## 5. 正式实现后的容量阶梯

配置：transport 4 连接共享订阅、EMQX `hash_clientid`、信箱 10000、inflight 1024、transport 批 512、
流水线 4 消费者。

**未合并最新值时：**

| 目标 | EMQX 收 | 丢弃 | 入库 | InfluxDB 行 | 失效 | 结论 |
|---|---|---|---|---|---|---|
| 7,000 | 839,998 | 0 | 839,998 | 839,998 | 0 | 通过 |
| 10,000 | 1,199,997 | 0 | 1,200,420 | 1,199,997 | 0 | 通过 |
| 14,000 | 1,679,993 | 10,330 | 909,680 | 909,680 | 17 | 失败 |

10,000 档 `latest` 1,856ms、占周期 55%，单条约 215µs。Redis 在 12,000 条/秒时实测峰值 91%，其中
**evalsha 占 58.9%**（989,857 次，约每条消息一次）、xadd 12.4%。Redis 一满，transport 的 XADD 排队，
回 PUBACK 变慢，EMQX 信箱又堆。

**合并最新值后：**

| 目标 | EMQX 收 | 丢弃 | 入库 | InfluxDB 行 | 失效 | 每批周期 | latest | 结论 |
|---|---|---|---|---|---|---|---|---|
| 10,000 | 1,200,000 | 0 | 1,200,201 | 1,200,000 | 0 | 942ms | 98ms | 通过 |
| 13,000 | 1,559,999 | 0 | 1,559,999 | 1,559,999 | 0 | 1,012ms | 101ms | 通过 |
| 16,000 | 1,920,000 | 0 | 1,498,501 | 1,498,501 | 6 | 971ms | 86ms | 失败 |

16,000 时流水线本身很健康，失败仍是连接被杀，排空仅 45 秒（无大积压）——消息在到达 Redis 前丢失。
Prometheus 回看 VM 整机 CPU：10,000 约 84%、13,000 约 92%、**16,000 为 96～97%**，1 分钟负载峰值 15。

## 6. 确认与主备切换

**13,000 重复：**

| | EMQX 收 | 丢弃 | 入库 | 失效 | influx 阶段 | 结论 |
|---|---|---|---|---|---|---|
| 第 1 次 | 1,560,000 | 141,827 | 958,934 | 10 | 1,056ms | 失败 |
| 第 2 次 | 1,557,397 | 0 | 1,557,397 | 0 | 642ms | 通过 |

连同阶梯中那次，**13,000 为 3 次 2 过**。

**主备切换**（10,000 条/秒，第 40 秒 `docker kill` 主 transport）：

| 口径 | 条数 |
|---|---|
| 客户端实发 | 1,199,999 |
| EMQX 接收 | 1,199,999 |
| EMQX 丢弃 | 0 |
| 流水线入库 | 1,201,741 |
| 死信 | 0 |
| **InfluxDB 行数** | **1,199,999** |

备实例约 25 秒后接管、4 条连接全部重连。入库多出的 1,742 条是重复：被杀瞬间已写入 Redis 但未回 PUBACK
的消息被 EMQX 重投给新主实例。InfluxDB 同设备同 ts 覆盖，最终行数等于实发数，**零丢失**。

**11,500 重复：**

| | EMQX 收 | 丢弃 | 入库 | InfluxDB 行 | 失效 | 每批周期 | 结论 |
|---|---|---|---|---|---|---|---|
| 第 1 次 | 1,379,994 | 0 | 1,380,907 | 1,379,994 | 0 | 1,251ms | 通过 |
| 第 2 次 | 1,379,995 | 0 | 1,379,995 | 1,379,995 | 0 | 939ms | 通过 |

第 1 次入库计数多出 913 条，是基线快照后处理掉的上一轮尾巴；InfluxDB 行数等于 EMQX 接收数。

## 7. 环境

| 项 | 值 |
|---|---|
| 被压 VM | VMware 虚拟机，8 vCPU / 7.6 GB，Rocky Linux 10.2，与发压机同一物理宿主 |
| 宿主 / 发压机 | i7-14700，20 核 28 线程，32 GB；`loadgen.py` 16 进程（实测与 28 进程吞吐一致，仅延迟差 23 倍） |
| 负载形态 | 600 条 MQTT 连接，每台按「目标 ÷ 600」条/秒，QoS 1，3 个测点 |
| 关键版本 | EMQX 5.10.5、InfluxDB 3 Core 3.12.0、Redis 7（`appendfsync always`） |

**口径限制**：600 条连接打 N 条/秒，不等于 N×10 台真实设备（真实设备约 10 秒一报）。总吞吐相同但连接数差两个
数量级，EMQX 维持海量连接的内存与调度开销、鉴权回调压力、在线状态写入量**均未测**。本报告的数只能说
「每秒处理多少条消息」，不能换算成「能接多少台设备」。

## 8. 未执行与已知盲区

- `MqttProtocolAdapterIT`、`ReliabilityE2EIT`、`LatestValueStoreIT`、`PlatformOverviewApiIT` 需要 Docker，开发机未运行。
  共享订阅的升级退订、最新值合并等关键语义改用压测机上的差分测试、实测订阅表、随机等价对照代替验证。
- VM 配置与仓库默认值不一致（信箱 10000、inflight 1024、transport 批 512 只在 VM 上）。按所有者决定暂不写入仓库默认值，
  因此**按仓库默认值部署无法复现本报告的数字**。
- 信箱 1000 与共享订阅的组合未测（不确定共享订阅后是否还需要调大信箱）。
